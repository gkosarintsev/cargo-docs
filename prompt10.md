## Контекст

Формируем каталог Architecture Decision Records (ADR) для фиксации фундаментальных инженерных выборов с их контекстом, компромиссами, альтернативами и последствиями.
Каждое решение должно отвечать на вопрос **«Почему именно так?»** (из §39 master-prompt) и рассматривать **минимум 2–3 альтернативы** с глубоким техническим сравнением.

Язык — **русский**.

---

## Задание 1: создай `docs/03-architecture/adr/0000-template.md`

Создай эталонный шаблон ADR с разделами:

- **Status**: Proposed / Accepted / Rejected / Deprecated / Superseded
- **Date**: Дата фиксации
- **Context & Problem Statement**: Контекст, ограничения, бизнес- и тех-драйверы
- **Decision Drivers**: Ключевые критерии выбора
- **Considered Options**: Рассмотренные альтернативы
- **Decision Outcome**: Выбранный вариант и детальное обоснование
- **Pros and Cons of the Options**: Сравнительная таблица/список плюсов и минусов каждого варианта
- **Consequences**: Положительные, отрицательные последствия и риски
- **Migration / Evolution Path**: План перехода при изменении условий

## Задание 2: создай ADR с 0001 по 0008

Для каждого файла используй созданный шаблон и глубоко проработай специфику задачи:

### 1. `ADR-0001: Выбор базового архитектурного стиля (Modular Monolith vs Microservices)`

- **Проблема**: Выбор структуры системы на старте проекта при высоких требованиях к масштабируемости в будущем.
- **Альтернативы**: Распределенные микросервисы сразу; Бесструктурный монолит; Модульный монолит с DDD-границами и асинхронным Outbox.
- **Решение**: Модульный монолит для MVP с четким разделением Bounded Contexts и подготовкой к выделению нагруженных сервисов на Фазе 2.

### 2. `ADR-0002: Выбор реляционной СУБД для транзакционного ядра (PostgreSQL)`

- **Проблема**: Выбор основного хранилища для заказов, финансов, профилей компаний и прав.
- **Альтернативы**: PostgreSQL; MySQL / MariaDB; MongoDB; Oracle.
- **Решение**: PostgreSQL (богатая экосистема, поддержка JSONB, PostGIS, строгий ACID, надежная репликация, зрелый pg_dump/WAL-G).

### 3. `ADR-0003: Выбор специализированного поискового движка (OpenSearch)`

- **Проблема**: Необходимость быстрого гео-поиска (по радиусу), фасетной фильтрации и ранжирования тысяч грузов и машин без перегрузки OLTP базы.
- **Альтернативы**: OpenSearch / Elasticsearch; Полнотекстовый поиск PostgreSQL (pg_trgm + PostGIS); Meilisearch; Typesense.
- **Решение**: OpenSearch (высокая производительность на больших объемах, поддержка гео-дистанций, встроенные агрегации, открытая лицензия).

### 4. `ADR-0004: Выбор платформы для шины событий и стриминга данных (Apache Kafka)`

- **Проблема**: Обеспечение надежной асинхронной доставки событий между контекстами, интеграции вебхуков и приема телеметрии.
- **Альтернативы**: Apache Kafka; RabbitMQ; NATS JetStream; Redis Streams.
- **Решение**: Apache Kafka (гарантия порядка в рамках партиции, replayability, высокая пропускная способность при пакетной обработке GPS).

### 5. `ADR-0005: Выбор объектного хранилища для документов и медиа (S3-compatible Object Storage)`

- **Проблема**: Надежное, недорогое и масштабируемое хранение скан-копий CMR, фото повреждений груза и PDF-счетов.
- **Альтернативы**: MinIO / Ceph S3 / AWS S3; Локальная файловая система / NFS; MongoDB GridFS; PostgreSQL BLOB (bytea).
- **Решение**: S3-совместимое объектное хранилище (MinIO для локала/онпрема, облачный S3 в проде).

### 6. `ADR-0006: Выбор архитектурного стиля внешнего и внутреннего API (REST + gRPC + Webhooks)`

- **Проблема**: Выбор протоколов взаимодействия между клиентами (Web/Mobile), бэкендом и внешними TMS.
- **Альтернативы**: Чистый REST/JSON; GraphQL; gRPC для всего; Гибридный подход (REST/JSON для публичного API, gRPC для внутреннего межсервисного, Webhooks для событий, WebSocket для real-time).
- **Решение**: Гибридный подход.

### 7. `ADR-0007: Стратегия аутентификации и авторизации (OAuth 2.0 + OIDC + JWT + API Keys)`

- **Проблема**: Безопасная аутентификация веб-пользователей, водителей мобильных приложений и серверных интеграций внешних TMS/ERP.
- **Альтернативы**: Session-cookie аутентификация; OAuth 2.0 / OIDC с JWT (Access/Refresh); Custom Header Tokens.
- **Решение**: OAuth 2.0 / OIDC с короткими JWT Access Tokens и ротируемыми Refresh Tokens в Redis + HMAC API Keys для B2B TMS.

### 8. `ADR-0008: Стратегия мультиарендности и изоляции данных (Multi-tenancy)`

- **Проблема**: Обеспечение строгой изоляции данных тысяч конкурирующих логистических компаний на одной платформе.
- **Альтернативы**: Database-per-Tenant (отдельная БД для каждой компании); Schema-per-Tenant (отдельная схема Postgres); Shared Database with Tenant ID Column & Row-Level Security (RLS).
- **Решение**: Shared Database с обязательным полем `organization_id`, индексированием и проверкой на уровне контекста приложения и RLS в Postgres.

## Важные замечания для выполнения

- Каждое решение должно содержать детальный анализ альтернатив, а не формальные отписки.
- Учитывай реальную специфику B2B логистики и маркетплейсов.
