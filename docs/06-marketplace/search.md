# Поисковая подсистема (Search Engine)

## 1. Архитектура поисковой подсистемы

Поиск грузов и транспорта — одна из самых критичных и высоконагруженных частей платформы.

### Почему не PostgreSQL?

Прямой поиск в транзакционной базе данных (PostgreSQL) не используется по следующим причинам:

- **Сложные пространственные (geo) запросы**: Вычисление расстояний на сфере (geo-distance), попадание в полигоны и поиск вдоль коридоров маршрутов крайне ресурсоемки для реляционных БД при больших объемах данных.
- **Полнотекстовый поиск и фасетная фильтрация**: Необходимость быстрого подсчета агрегаций (сколько грузов определенного типа кузова доступно) и сложной фильтрации по множеству слабоструктурированных параметров.
- **Требования к производительности**: Необходимость обеспечения субсекундного отклика (менее 100 мс) при высоких нагрузках (тысячи RPS).
- **Изоляция нагрузки**: Разделение транзакционной нагрузки (создание/обновление грузов) и аналитико-поисковой нагрузки (чтение списков выдачи).

Для решения этих задач применяется поисковый движок **OpenSearch** (или Elasticsearch).

### Пайплайн индексации

Для обеспечения отказоустойчивости и консистентности используется асинхронный паттерн Transactional Outbox:

1. **PostgreSQL**: При создании или изменении груза транзакционно обновляется бизнес-сущность и добавляется запись в таблицу `outbox`.
2. **Debezium / Outbox Poller**: Читает таблицу `outbox` и отправляет события об изменениях.
3. **Kafka (топик `load.events`)**: Выступает надежным брокером сообщений и буфером.
4. **OpenSearch Consumer (Indexer)**: Микросервис вычитывает события из Kafka, агрегирует (batching) и обновляет документы в индексе `loads_v1`.

## 2. Структура документа в поисковом индексе (OpenSearch Mapping)

Документ, описывающий груз, оптимизирован для быстрого поиска и содержит как точные координаты, так и массивы атрибутов.

```json
{
  "mappings": {
    "properties": {
      "id": { "type": "keyword" },
      "organization_id": { "type": "keyword" },

      "geo_origin": { "type": "geo_point" },
      "geo_destination": { "type": "geo_point" },
      "route_polygon": { "type": "geo_shape" },

      "pickup_date": {
        "type": "date_range",
        "format": "yyyy-MM-dd"
      },

      "body_types": { "type": "keyword" },

      "weight_kg": { "type": "integer" },
      "volume_m3": { "type": "float" },

      "price": { "type": "long" },
      "adr_class": { "type": "keyword" },

      "tags": { "type": "keyword" },

      "is_private": { "type": "boolean" },
      "allowed_org_ids": { "type": "keyword" },

      "created_at": { "type": "date" },
      "status": { "type": "keyword" }
    }
  }
}
```

## 3. Типы поисковых запросов

### Geo-radius Search

Поиск грузов в заданном радиусе $R$ км от определенной точки (города, текущих координат водителя).
Используется фильтр `geo_distance` по полю `geo_origin`.

### Route Corridor Search

Поиск грузов (догруза/попутного груза), которые находятся вдоль запланированного маршрута движения транспортного средства.
Формируется полигон маршрута (коридор шириной $W$ км, например 50 км по обе стороны от трассы), и выполняется запрос типа `geo_shape` с отношением `INTERSECTS` или `WITHIN` к полю `geo_origin` или точкам маршрута.

### Faceted Filtering (Фасетная фильтрация)

Комбинированная фильтрация по множеству параметров с одновременным подсчетом доступных вариантов (фасетов):

- **Тип кузова** (`body_types`): Тент, Рефрижератор, Изотерм и т.д.
- **Грузоподъемность** (`weight_kg`): Поиск грузов, вес которых меньше или равен грузоподъемности машины.
- **Наличие гидроборта**, **Тип оплаты** и прочие флаги (`tags`).

## 4. Консистентность и обновление индексов

- **Eventual Consistency**: Архитектура подразумевает согласованность в конечном счете. Задержка между обновлением в PostgreSQL и появлением в OpenSearch обычно составляет менее 1 секунды. Клиентские приложения проектируются с учетом этого факта (например, оптимистичные UI-обновления).
- **Дедупликация событий**: В случае повторной доставки сообщений из Kafka (at-least-once delivery), консьюмер выполняет идемпотентные операции обновления (`doc_as_upsert`). Для разрешения конфликтов версий используется поле `updated_at` (versioning) из бизнес-сущности.
- **Стратегия Reindexing без даунтайма**: При необходимости изменить маппинг индекса (добавление новых анализаторов, изменение типов данных):
  1. Создается новый индекс (например, `loads_v2`).
  2. Запускается процесс переиндексации данных из БД или старого индекса.
  3. Новые события из Kafka пишутся в оба индекса (или только в новый, если переиндексация атомарна).
  4. После завершения, алиас (Alias) для чтения `loads_read` атомарно переключается с `loads_v1` на `loads_v2`.
