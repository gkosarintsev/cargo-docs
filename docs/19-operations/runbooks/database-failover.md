# Runbook: Аварийное переключение PostgreSQL

## 1. Симптомы и триггеры алертов
- **Алерт**: `PostgresPrimaryDown` (P1)
- **Симптом**: Primary нода не отвечает > 30 сек, 500 ошибки при мутирующих API запросах.

## 2. Диагностика
Проверка состояния Patroni:
```bash
kubectl exec -it <patroni-pod> -- patronictl list
kubectl logs -l app=patroni -c patroni
```

## 3. Стратегия деградации
Система автоматически переходит в Read-Only режим для пользователей (кеш/OpenSearch). Операции создания грузов/заказов возвращают `503 Service Unavailable`.

## 4. Пошаговый алгоритм восстановления
Обычно failover происходит автоматически через Patroni. При ручном переключении (если кворум сломан):
```bash
patronictl switchover
# Выбрать активную реплику для промоута
```

## 5. Проверка корректности восстановления
```sql
SELECT pg_is_in_recovery();
-- На Primary должно вернуть `f` (false)
```

## 6. Пост-действия
Обновление Post-Mortem. Расследование причины падения Primary ноды.
