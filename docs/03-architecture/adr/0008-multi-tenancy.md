# ADR-0008: Стратегия мультиарендности и изоляции данных (Multi-tenancy)

**Status**: Accepted

**Date**: 2023-10-25

## Context & Problem Statement

Платформа является B2B SaaS-маркетплейсом, где будут работать тысячи логистических компаний, грузоотправителей и перевозчиков. Критически важно гарантировать, что данные одной компании (теннанта) никогда не будут доступны другой компании из-за ошибки в коде. Требуется выбрать подход к изоляции данных в базе данных.

## Decision Drivers

- Исключение риска утечки или смешивания данных между клиентами.
- Операционная простота (управление миграциями, резервное копирование).
- Экономическая эффективность использования ресурсов СУБД.
- Масштабируемость до десятков тысяч тенантов.

## Considered Options

1. **Database-per-Tenant**: Каждой компании — своя физическая/логическая БД.
2. **Schema-per-Tenant**: Одна БД, но у каждой компании своя схема (свои таблицы).
3. **Shared Database with Tenant ID**: Все компании хранятся в одных таблицах, разделение происходит по столбцу `organization_id` + Row-Level Security (RLS).

## Decision Outcome

**Выбранный вариант:** Shared Database с обязательным полем `organization_id`, индексом и Row-Level Security (RLS) в Postgres.

**Обоснование (Почему именно так?):**
Подходы с отдельной БД или схемой на клиента отлично подходят для Enterprise решений, где клиентов немного, но их данные огромны, или где требуются строгие compliance-регуляции. В нашем случае это маркетплейс, где клиентов будут тысячи. Управление тысячами схем или баз сделает процесс миграции схемы БД (schema evolution) практически невыполнимым (потребуются часы на накатывание миграции).
Поэтому мы выбираем подход Shared Database. Чтобы компенсировать риск ошибки разработчика (забыл добавить `WHERE organization_id = X` в запрос), мы активируем на уровне PostgreSQL фичу **Row-Level Security (RLS)**. При открытии соединения приложение будет задавать контекст тенанта (например, через `set_config('app.current_tenant', '123')`), и база сама отфильтрует строки.

## Pros and Cons of the Options

### Shared Database + Tenant ID + RLS

- Плюсы:
  - Одна схема базы данных, легкие и быстрые миграции структуры.
  - Высокая утилизация ресурсов, экономичность.
  - RLS на уровне СУБД гарантирует, что баг в ORM не приведет к утечке данных.
- Минусы:
  - В случае "шумного соседа" (noisy tenant) страдает производительность всех остальных, так как ресурсы общие.
  - RLS добавляет небольшой оверхед на планировщик запросов PostgreSQL.

### Schema-per-Tenant / Database-per-Tenant

- Плюсы:
  - Максимальная физическая изоляция.
  - Легко восстановить из бэкапа данные только одного клиента.
  - Защита от noisy neighbor.
- Минусы:
  - При тысячах клиентов миграции становятся кошмаром (нужно применить ALTER TABLE 10000 раз).
  - Потребление памяти (Postgres создает отдельный кэш для каждой таблицы в каждой схеме).

## Consequences

- **Положительные:** Мы сможем легко бордить новых клиентов и управлять схемой данных. Уровень изоляции при использовании RLS будет достаточным для нашего класса системы.
- **Отрицательные:** Необходимость разработать инфраструктурный код в приложении, который будет пробрасывать tenant ID из JWT-токена прямо в контекст сессии PostgreSQL перед выполнением бизнес-запросов.
- **Риски:** Если не настроить правильное индексирование (например, составные индексы `(organization_id, created_at)`), запросы могут сильно тормозить при росте общего объема данных.

## Migration / Evolution Path

Архитектура Shared Database позволит нам легко развиваться. Если в будущем появится крупный Enterprise-клиент, который потребует физической изоляции (compliance), мы всегда сможем выделить его данные в отдельный кластер БД (перейти к гибридной модели) без изменения бизнес-логики приложения (так как RLS и tenant_id уже вшиты в ядро).
