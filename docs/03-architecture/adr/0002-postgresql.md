# ADR-0002: Выбор реляционной СУБД для транзакционного ядра (PostgreSQL)

**Status**: Accepted

**Date**: 2023-10-25

## Context & Problem Statement

Необходимо выбрать основное хранилище данных для ядра системы, которое включает управление заказами, финансовые транзакции, профили компаний и управление доступом. Эти домены требуют строгой консистентности, поддержки сложных связей и гарантии сохранности данных (ACID). Также требуется гибкость для хранения полуструктурированных данных (например, метаданных заказов) и поддержка геоданных.

## Decision Drivers

- Строгие гарантии транзакционности (ACID) для финансовых и бизнес-важных операций.
- Поддержка полуструктурированных данных и расширяемых форматов.
- Надежность, отказоустойчивость и наличие проверенных инструментов резервного копирования.
- Большое сообщество, доступность специалистов на рынке.
- Богатая экосистема расширений (в особенности для гео-функций).

## Considered Options

1. **PostgreSQL**: Мощная ORDBMS, de facto стандарт для современных веб-приложений.
2. **MySQL / MariaDB**: Популярная реляционная СУБД, отличная производительность на чтение.
3. **MongoDB**: Документоориентированная NoSQL СУБД.
4. **Oracle Database**: Энтерпрайз-решение с огромным функционалом, но высокой стоимостью.

## Decision Outcome

**Выбранный вариант:** PostgreSQL.

**Обоснование (Почему именно так?):**
PostgreSQL идеально закрывает все требования нашего транзакционного ядра. Во-первых, он обеспечивает строгий ACID, что абсолютно критично для финансовых модулей и статусов заказов. Во-вторых, встроенная поддержка типа `JSONB` позволяет гибко хранить неструктурированные данные (например, динамические атрибуты грузов) без потери возможности индексации. В-третьих, расширение `PostGIS` предоставляет непревзойденные возможности для базовых гео-вычислений и хранения координат. PostgreSQL обладает зрелыми инструментами (pg_dump, WAL-G) для бекапов и надежной репликацией. Бесплатная лицензия и огромное сообщество делают его самым прагматичным выбором.

## Pros and Cons of the Options

### PostgreSQL

- Плюсы:
  - Полное соответствие ACID, отличная поддержка конкурентного доступа (MVCC).
  - Расширения, такие как PostGIS и поддержка JSONB.
  - Зрелость, надежность, мощные инструменты резервного копирования.
- Минусы:
  - Требует тонкой настройки (tuning параметров конфигурации).
  - Vacuum может потребовать внимания при высокой частоте обновлений строк.

### MySQL / MariaDB

- Плюсы:
  - Простота настройки, исторически хороша для простых веб-сайтов.
  - Хорошая производительность.
- Минусы:
  - Ограниченные возможности для сложных аналитических и гео-запросов по сравнению с Postgres.
  - Поддержка JSON и строгих транзакций местами уступает PostgreSQL в гибкости.

### MongoDB

- Плюсы:
  - Гибкая схема (schema-less), легко масштабируется горизонтально.
- Минусы:
  - Сложности с многодокументными ACID транзакциями (хоть они и есть в новых версиях, это не нативный паттерн).
  - Не подходит для сложных реляционных связей между заказами, счетами и пользователями (требуется нормализация).

### Oracle Database

- Плюсы:
  - Выдающиеся возможности масштабирования, надежности и фичи корпоративного уровня.
- Минусы:
  - Крайне высокая стоимость лицензий.
  - Требует специфичных, дорогих специалистов (DBA).

## Consequences

- **Положительные:** Мощная база данных, покрывающая 95% нужд проекта "из коробки". Возможность использовать одни и те же инструменты для реляционных, JSON и гео-данных на ранних этапах проекта.
- **Отрицательные:** Нужно вложиться в экспертизу по настройке Autovacuum и пулинга соединений (например, PgBouncer) для высоких нагрузок.
- **Риски:** Использование сложных SQL конструкций может привязать логику приложения к специфике PostgreSQL.

## Migration / Evolution Path

На старте PostgreSQL будет использоваться как единый кластер с логическим разделением схем (schema-per-module) для каждого Bounded Context. По мере роста, если одному из контекстов потребуется собственное хранилище или другие характеристики масштабирования, данные этого модуля будут мигрированы в отдельный кластер PostgreSQL (или специализированную СУБД), а интеграция будет проходить через CDC (Change Data Capture, например Debezium).
