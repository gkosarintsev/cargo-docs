# ADR-0014: Стек сбора телеметрии и наблюдаемости (Observability)

## Статус

Принято

## Контекст

С ростом количества микросервисов, а также из-за их распределенной природы, усложняется процесс поиска первопричин сбоев (Root Cause Analysis). Разработчикам и SRE инженерам необходим единый стандарт и инструментарий для работы с тремя столпами наблюдаемости (Observability): метриками, логами и распределенными трассировками (traces).

## Рассмотренные альтернативы

1. **Разрозненные проприетарные агенты (Datadog/NewRelic)**: Отличный функционал из коробки, но высокий риск vendor lock-in и потенциально непредсказуемый рост затрат при масштабировании (оплата за хосты/гигабайты/события).
2. **Vendor-agnostic стандарт OpenTelemetry (OTel) + Prometheus / Grafana / Loki / Tempo**: Использование открытых стандартов для сбора и агрегации телеметрии, с возможностью гибко менять backend для хранения.

## Решение

Мы выбираем **OpenTelemetry Instrumentation + стэк LGTM (Loki, Grafana, Tempo, Mimir/Prometheus)**.

### Обоснование

- **Vendor-agnostic**: OpenTelemetry является индустриальным стандартом. Приложения инструментируются с использованием OTel SDK (или авто-инструментации), что позволяет не привязываться к конкретному хранилищу.
- **Единый конвейер**: Использование OpenTelemetry Collector позволяет централизованно управлять батчингом, фильтрацией, сэмплированием и маршрутизацией всех видов телеметрии (Traces, Metrics, Logs).
- **Стек хранения**:
  - Метрики: **Prometheus** (или Mimir для долговременного хранения).
  - Логи: **Grafana Loki** (дешевле Elasticsearch для логов, так как индексирует только метаданные/лейблы).
  - Трейсы: **Grafana Tempo**.
  - Визуализация: **Grafana** (бесшовная корреляция метрик, логов и трейсов).

## Последствия

### Положительные

- Отсутствие привязки к конкретному вендору мониторинга.
- Снижение затрат на хранение логов за счет выбора Loki.
- Сквозная трассировка запросов через все микросервисы и брокеры сообщений (Trace Context propagation).

### Риски и их митигация

- **Риск**: Огромный объем генерируемых трейсов (High volume of Trace Data) в высоконагруженных сервисах (например, GPS Ingestion).
  **Митигация**: Настройка агрессивного сэмплирования (Head-based или Tail-based sampling) на уровне OTel Collector: сохранять 100% трейсов с ошибками и только 1-5% успешных запросов.
- **Риск**: Затраты ресурсов на инструментирование каждого нового сервиса.
  **Митигация**: Предоставление стандартизированных корпоративных библиотек/шаблонов для быстрого старта (Service Templates) с уже настроенным OTel.
