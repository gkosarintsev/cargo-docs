# ADR-0013: Стратегия многоуровневого кэширования (Multi-tier Caching)

## Статус

Принято

## Контекст

Высокая нагрузка на базу данных при частом чтении справочной информации, профилей пользователей, настроек и активных сессий требует оптимизации. Необходимо снизить задержку ответов (latency) и потребление ресурсов СУБД, при этом обеспечивая приемлемый уровень актуальности (свежести) данных для конечных пользователей.

## Рассмотренные альтернативы

1. **Отсутствие кэширования**: Все запросы идут в БД. Приводит к перегрузке БД и высоким задержкам на чтении.
2. **Только локальный in-memory кэш приложения**: Быстро, но ведет к рассогласованию данных между разными экземплярами (подами) одного микросервиса.
3. **Распределенный Redis-кэш со стратегией Cache-Aside + Event-Driven Cache Eviction**: Использование единого распределенного кэша с асинхронной инвалидацией.

## Решение

Мы выбираем **распределенный Redis кэш со стратегией Cache-Aside и подпиской на Domain Events для точечной инвалидации**.

### Обоснование

- **Cache-Aside (Lazy Loading)**: Приложение сначала ищет данные в Redis. При промахе (cache miss) идет в БД, затем сохраняет результат в кэш с определенным TTL. Это надежный и простой в реализации паттерн.
- **Event-Driven Eviction**: При изменении данных в БД микросервис-владелец публикует доменное событие (например, `UserProfileUpdated`). Сервисы, кэширующие эти данные, подписываются на событие и принудительно инвалидируют (удаляют) соответствующие ключи в Redis.
- Допускается использование **локального кэша** (Caffeine/Gocache) поверх Redis только для сверхчастых и редко меняющихся справочников с очень коротким TTL, чтобы избежать сетевого overhead.

## Последствия

### Положительные

- Значительное снижение нагрузки на чтение с базы данных PostgreSQL.
- Уменьшение времени ответа API.
- Эффективное использование памяти за счет кэширования только востребованных данных (Lazy Loading).

### Риски и их митигация

- **Риск**: Проблема неконсистентности данных (Stale data) при сбоях в доставке событий инвалидации.
  **Митигация**: Использование Time-to-Live (TTL) как запасного механизма (fallback) для всех кэшируемых записей.
- **Риск**: Проблема Thundering Herd (шторм запросов к БД при массовом устаревании популярного ключа).
  **Митигация**: Использование вероятностного устаревания (probabilistic early expiration) или мьютексов на обновление кэша.
- **Риск**: Дополнительная точка отказа в виде кластера Redis.
  **Митигация**: Развертывание Redis в режиме High Availability (Redis Sentinel / Cluster) и graceful degradation (возврат к чтению из БД при недоступности кэша).
