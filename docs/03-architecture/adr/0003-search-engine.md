# ADR-0003: Выбор специализированного поискового движка (OpenSearch)

**Status**: Accepted

**Date**: 2023-10-25

## Context & Problem Statement

Платформа представляет собой маркетплейс грузоперевозок, что подразумевает наличие тяжелого, сложного поиска. Пользователям необходимо быстро искать грузы и машины по множеству критериев: гео-поиск (в заданном радиусе от точки), фильтрация по датам, типу транспорта, фасетная фильтрация, и полнотекстовый поиск по описаниям. Объем данных будет быстро расти (тысячи и миллионы записей). Выполнение таких запросов на основной OLTP базе (PostgreSQL) приведет к деградации производительности транзакционного ядра.

## Decision Drivers

- Высокая скорость выполнения сложных комбинированных запросов (гео + полнотекст + фильтры).
- Способность масштабироваться горизонтально при росте объема индекса.
- Разгрузка основной базы данных (PostgreSQL).
- Наличие развитого API и экосистемы агрегаций для построения фасетов.

## Considered Options

1. **OpenSearch / Elasticsearch**: Полноценные поисковые движки на базе Lucene, созданные для полнотекстового и структурированного поиска.
2. **Полнотекстовый поиск PostgreSQL (pg_trgm + PostGIS)**: Использование встроенных возможностей основной СУБД.
3. **Meilisearch**: Легкий и сверхбыстрый поисковик, ориентированный на мгновенный поиск.
4. **Typesense**: Альтернатива Algolia, быстрый in-memory/disk поисковик.

## Decision Outcome

**Выбранный вариант:** OpenSearch.

**Обоснование (Почему именно так?):**
Для маркетплейса логистики критически важна комбинация точного гео-поиска, сложных многомерных фильтров и возможности ранжирования результатов. OpenSearch (как open-source форк Elasticsearch от AWS) предоставляет мощнейший функционал агрегаций для фасетов (например, показать количество грузов по типам транспорта) и превосходно справляется с гео-дистанциями на огромных массивах данных. Использование PostgreSQL для этих задач быстро упрется в ограничения индексов и нагрузит CPU транзакционной базы. OpenSearch имеет открытую лицензию (Apache 2.0), горизонтально масштабируется и является отраслевым стандартом для подобных задач.

## Pros and Cons of the Options

### OpenSearch / Elasticsearch

- Плюсы:
  - Высокая производительность и масштабируемость на терабайтах данных.
  - Встроенные продвинутые гео-запросы и агрегации (фасеты).
  - Богатая экосистема (Logstash, Kibana/Dashboards для аналитики).
- Минусы:
  - Сложнее в настройке и эксплуатации по сравнению с легковесными движками.
  - Требует значительных ресурсов оперативной памяти (JVM).

### Полнотекстовый поиск PostgreSQL

- Плюсы:
  - Нет необходимости внедрять и поддерживать новую инфраструктурную единицу.
  - Данные всегда консистентны, не нужен процесс синхронизации (CDC).
- Минусы:
  - Сложности с фасетным поиском и ранжированием сложных комбинированных запросов.
  - Запросы на поиск "съедают" ресурсы OLTP-базы, мешая транзакциям.

### Meilisearch / Typesense

- Плюсы:
  - Очень быстрая настройка, отличный опыт для разработчиков.
  - Мгновенный отклик (typo-tolerance).
- Минусы:
  - Гео-возможности и сложные агрегации ограничены по сравнению с OpenSearch/Elastic.
  - Не так хорошо масштабируются на сотни миллионов сложных документов с частыми обновлениями.

## Consequences

- **Положительные:** Мы обеспечим пользователям молниеносный и релевантный поиск грузов и машин. Основная транзакционная БД (Postgres) не будет страдать от тяжелых поисковых запросов.
- **Отрицательные:** Усложнение архитектуры. Потребуется механизм синхронизации данных между PostgreSQL и OpenSearch (через брокер событий или CDC, например Debezium). Задержка консистентности (eventual consistency) между созданием груза и его появлением в поиске.
- **Риски:** Рассинхронизация индексов и источника правды (БД), что потребует механизмов полной переиндексации (reindexing).

## Migration / Evolution Path

На первом этапе синхронизация данных в OpenSearch будет происходить через события из Outbox паттерна в модуле публикации грузов. В дальнейшем планируется переход на Change Data Capture (Debezium + Kafka) для автоматического и надежного зеркалирования изменений из PostgreSQL в OpenSearch.
