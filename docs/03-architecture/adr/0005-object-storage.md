# ADR-0005: Выбор объектного хранилища для документов и медиа (S3-compatible Object Storage)

**Status**: Accepted

**Date**: 2023-10-25

## Context & Problem Statement

Логистическая платформа генерирует огромное количество неструктурированных файлов: скан-копии накладных (CMR, ТТН), фотографии повреждений груза с мобильных устройств, PDF-счета и закрывающие документы. Эти файлы необходимо надежно хранить, обеспечивать контроль доступа (приватные и публичные ссылки) и масштабировать хранилище независимо от основной базы данных.

## Decision Drivers

- Горизонтальная масштабируемость хранилища до сотен терабайт.
- Низкая стоимость хранения гигабайта данных по сравнению с блочными хранилищами СУБД.
- Унифицированный API для загрузки/выгрузки и управления доступом (pre-signed URLs).
- Возможность развертывания как в облаке (Cloud), так и в собственном дата-центре (On-premise).

## Considered Options

1. **S3-compatible Object Storage (MinIO, AWS S3, Ceph)**: Объектное хранилище с доступом по HTTP REST API S3.
2. **Локальная файловая система / NFS**: Хранение файлов на дисках серверов приложений.
3. **MongoDB GridFS**: Сохранение файлов внутри NoSQL БД.
4. **PostgreSQL BLOB (bytea)**: Сохранение бинарных данных прямо в реляционной таблице.

## Decision Outcome

**Выбранный вариант:** S3-совместимое объектное хранилище (MinIO для локала/онпрема, облачный S3 в проде).

**Обоснование (Почему именно так?):**
Протокол Amazon S3 стал стандартом индустрии для хранения объектов. Использование S3 API отвязывает наше приложение от конкретного вендора. В локальной среде или при развертывании on-premise мы будем использовать MinIO, а в облаке сможем переключиться на управляемый сервис (AWS S3, Yandex Object Storage) без изменения кода (достаточно поменять credentials). Объектное хранилище решает проблему загрузки дисков приложений, позволяет генерировать временные ссылки (pre-signed URLs) для скачивания приватных документов напрямую клиентом (минуя наш бэкенд), и предоставляет дешевое хранилище для петабайтов данных.

## Pros and Cons of the Options

### S3-compatible Object Storage (MinIO / AWS S3)

- Плюсы:
  - Де-факто индустриальный стандарт, поддерживается всеми языками программирования (SDK).
  - Бесконечное горизонтальное масштабирование.
  - Разгрузка бэкенда за счет прямой загрузки/скачивания клиентом по signed URL.
- Минусы:
  - Eventual consistency при удалении или перезаписи объектов.
  - Задержки (latency) при обращении по HTTP выше, чем при чтении с локального диска.

### Локальная файловая система / NFS

- Плюсы:
  - Простота реализации на старте.
  - Минимальная задержка при доступе.
- Минусы:
  - Ужасный опыт при масштабировании приложений (stateless vs stateful контейнеры).
  - Сложности с бекапами, риск потери данных при выходе из строя сервера.

### Базы данных (PostgreSQL bytea / GridFS)

- Плюсы:
  - Файлы бекапятся вместе с транзакционными данными (консистентность).
- Минусы:
  - Невероятно дорогое хранение в пересчете на ГБ.
  - Засорение буферов СУБД, катастрофическая деградация производительности базы.

## Consequences

- **Положительные:** Масштабируемое, надежное хранилище. Бэкенд остается stateless-приложением, что упрощает развертывание в Kubernetes. Экономия ресурсов БД.
- **Отрицательные:** Введение дополнительного компонента инфраструктуры, который нужно бекапить и мониторить (если используем MinIO self-hosted).
- **Риски:** Если не настроить правильные политики доступа (Bucket Policies), приватные документы компаний могут утечь в открытый доступ.

## Migration / Evolution Path

Для локальной разработки будет использоваться Docker-контейнер MinIO. В production-среде (особенно в облаке) трафик к S3 будет дополнительно кэшироваться через CDN для статических публичных файлов (например, аватарок), тогда как приватные документы будут отдаваться строго по short-lived signed URLs.
