# ADR-0004: Выбор платформы для шины событий и стриминга данных (Apache Kafka)

**Status**: Accepted

**Date**: 2023-10-25

## Context & Problem Statement

Для реализации паттерна "Модульный монолит", а в будущем и микросервисной архитектуры, нам необходим надежный механизм асинхронного взаимодействия между компонентами (Bounded Contexts). Модули должны обмениваться событиями (Domain Events) без жесткой связности. Кроме того, система должна справляться с приемом высокочастотной телеметрии (GPS-координаты машин от мобильных приложений) и надежной доставкой вебхуков во внешние системы (TMS клиентов).

## Decision Drivers

- Гарантия доставки и сохранения порядка сообщений (Ordering).
- Высокая пропускная способность для обработки потока телеметрии (GPS).
- Возможность повторного воспроизведения событий (Replayability) для аудита или восстановления состояния.
- Надежность кластеризации и отказоустойчивость.

## Considered Options

1. **Apache Kafka**: Распределенный лог коммитов, стандарт де-факто для потоковой передачи данных.
2. **RabbitMQ**: Классический брокер сообщений с поддержкой сложных маршрутизаций (AMQP).
3. **NATS JetStream**: Высокопроизводительная система обмена сообщениями.
4. **Redis Streams**: Легковесное решение на базе in-memory структуры.

## Decision Outcome

**Выбранный вариант:** Apache Kafka.

**Обоснование (Почему именно так?):**
Apache Kafka выбрана из-за её архитектуры распределенного лога, которая обеспечивает персистентность сообщений на диске и возможность их повторного чтения (replayability) разными консьюмерами в разное время. Это критично для Event-Driven архитектуры, где новый модуль может "прочитать" историю системы с нуля. Kafka обеспечивает строгую гарантию порядка сообщений в рамках партиции (например, все изменения по одному заказу обрабатываются строго последовательно), а также обладает непревзойденной пропускной способностью при пакетной (batch) обработке телеметрии GPS. RabbitMQ лучше подходит для сложных роутингов (коммутатор), но уступает Kafka в долговременном хранении стримов и масштабируемости консьюмеров.

## Pros and Cons of the Options

### Apache Kafka

- Плюсы:
  - Невероятно высокая пропускная способность, идеальна для стриминга (GPS телеметрия).
  - Persistent storage сообщений (можно хранить дни/недели) и replayability.
  - Гарантия порядка в рамках partition.
- Минусы:
  - Высокий порог входа и сложность кластерного развертывания (хотя KRaft упростил это).
  - Избыточна для простых fire-and-forget задач.

### RabbitMQ

- Плюсы:
  - Сложная маршрутизация сообщений через exchanges.
  - Понятный интерфейс управления, простота настройки на ранних этапах.
- Минусы:
  - Сообщения удаляются после успешной обработки, нет легкого replay'а.
  - Масштабирование очередей сложнее, чем партиционирование в Kafka.

### NATS JetStream

- Плюсы:
  - Очень высокая скорость, легковесный бинарник.
- Минусы:
  - Меньшая экосистема и интеграция с enterprise-инструментами (Kafka Connect).
  - Меньше специалистов на рынке с опытом эксплуатации под высокой нагрузкой.

## Consequences

- **Положительные:** Мы получаем надежную нервную систему для нашей архитектуры, готовую к гигантским объемам телеметрии и надежной интеграции модулей.
- **Отрицательные:** Необходимость поддерживать кластер Kafka (минимум 3 брокера для надежности), что требует компетенций в DevOps/SRE.
- **Риски:** Неправильный дизайн партиций или ключей сообщений может привести к нарушению порядка обработки (out-of-order processing) или неравномерной нагрузке.

## Стратегия партиционирования (Partition Key Policy)

Для гарантии строгой хронологии (Strict Total Ordering) событий одного объекта в пределах партиции устанавливаются обязательные правила формирования ключа `record.key`:

| Топик Kafka | Partition Key | Гарантия |
| :--- | :--- | :--- |
| `marketplace.loads.v1` | `load_id` (UUID) | Все изменения статуса одного груза обрабатываются строго по очереди |
| `marketplace.offers.v1` | `load_id` (UUID) | Защита от race conditions при параллельном акцепте ставок |
| `transport.orders.v1` | `order_id` (UUID) | Строгая последовательность смены статусов рейса (ASSIGNED -> AT_PICKUP -> ...) |
| `telemetry.gps.v1` | `vehicle_id` (UUID) | Точки трека одной машины всегда попадают в один поток консьюмера |
| `billing.settlement.v1` | `organization_id` (UUID) | Баланс и кредитный лимит организации пересчитываются сериализованно |

## Регламент обработки сбоев: Retry Topics & Dead-Letter Topic (DLT)

Для предотвращения блокировки (Head-of-Line Blocking) консьюмеров при возникновении транзиентных сетевых сбоев или ошибок валидации реализуется паттерн **Non-blocking Retry & DLT**:

```
[Main Topic] 
     │ (Ошибка обработки)
     ▼
[Topic.retry-1]  (Пауза 1 секунда, Backoff)
     │ (Повторная ошибка)
     ▼
[Topic.retry-2]  (Пауза 5 секунд, Backoff)
     │ (Повторная ошибка)
     ▼
[Topic.retry-3]  (Пауза 30 секунд, Backoff)
     │ (Неустранимая ошибка / Poison Pill)
     ▼
[Topic.dlt]      (Dead-Letter Topic -> Алерт в Sentry/OpsGenie)
```

### Заголовки сообщения в DLT (Kafka Record Headers):
1. `x-original-topic`: имя исходного топика (например, `transport.orders.v1`).
2. `x-original-partition`: номер исходной партиции.
3. `x-original-offset`: смещение в исходной партиции.
4. `x-exception-message`: краткое описание ошибки (например, `PostgreSQLException: connection timeout`).
5. `x-exception-stacktrace`: полный стектрейс исключения.
6. `x-retry-count`: суммарное количество попыток (значение `3`).
7. `x-failed-at`: ISO8601 таймстемп перемещения в DLT.

### Мониторинг и Redrive:
- Метрика Prometheus: `kafka_consumer_dlt_messages_total{topic, consumer_group}`. При превышении порога $>0$ срабатывает P2 алерт дежурному инженеру.
- Утилита повторного прогона (CLI Redrive): `cargo-cli kafka redrive --dlt transport.orders.v1.dlt --target transport.orders.v1 --batch 50`.

## Migration / Evolution Path

На Фазе 1 Kafka используется для асинхронного обмена доменными событиями между модулями через Transactional Outbox паттерн в PostgreSQL (`outbox_events`). В будущем планируется использование Kafka Connect и Debezium (CDC) для прямой потоковой трансляции лога изменений БД.
