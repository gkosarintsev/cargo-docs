# ADR-0007: Стратегия аутентификации и авторизации (OAuth 2.0 + OIDC + JWT + API Keys)

**Status**: Accepted

**Date**: 2023-10-25

## Context & Problem Statement

К платформе будут обращаться разные типы субъектов:

1. Пользователи через веб-браузер (менеджеры, логисты, диспетчеры).
2. Водители через мобильное приложение.
3. Сторонние серверы (B2B интеграции с ERP/TMS клиентов).
   Требуется единый, безопасный и стандартный механизм идентификации, аутентификации и авторизации (RBAC/ABAC).

## Decision Drivers

- Безопасность при работе в недоверенных сетях (мобильные устройства).
- Масштабируемость без привязки сессии к конкретному серверу приложений (stateless API).
- Поддержка межсервисной аутентификации.
- Простота и стандартность интеграции для B2B-клиентов.

## Considered Options

1. **Session-cookie аутентификация (Stateful)**: Хранение сессий в БД или Redis.
2. **OAuth 2.0 / OIDC с JWT (Access/Refresh Tokens)**: Stateless-подход для аутентификации пользователей.
3. **Custom Header Tokens**: Самописное управление токенами в БД.

## Decision Outcome

**Выбранный вариант:** OAuth 2.0 / OIDC с короткими JWT Access Tokens и ротируемыми Refresh Tokens в Redis + HMAC API Keys для B2B TMS.

**Обоснование (Почему именно так?):**
Для пользователей и водителей мы используем стандартный протокол OAuth 2.0 с расширением OIDC. Клиенты получают JWT (JSON Web Token) как Access Token, который валидируется бэкендом (или API Gateway) без похода в базу, что дает огромный прирост производительности (stateless). Так как JWT нельзя отозвать до истечения его короткого срока жизни (обычно 15-30 минут), мы используем длинные Refresh Tokens, которые хранятся в Redis, чтобы можно было принудительно разлогинить устройство.
Для B2B-интеграций (Service-to-Service вызовы из чужих серверов) OIDC избыточен и сложен в поддержке для клиентов. Поэтому для них мы выдаем долгоживущие статические API Keys, подписанные HMAC, которые передаются в заголовке `Authorization: ApiKey ...`.

## Pros and Cons of the Options

### OAuth 2.0 / OIDC + JWT

- Плюсы:
  - Stateless Access Tokens, нет обращений к базе при каждом запросе.
  - Индустриальный стандарт, понятный большинству фронтенд- и мобайл-разработчиков.
  - Удобно пробрасывать контекст пользователя во внутренние микросервисы.
- Минусы:
  - Проблема инвалидации токена до его истечения (решается коротким TTL и refresh токенами).
  - JWT может быть большим, что немного увеличивает размер HTTP-заголовка.

### Session-cookie (Stateful)

- Плюсы:
  - Простая инвалидация сессии (просто удаляем из базы/Redis).
  - Защита от XSS, если использовать HttpOnly cookies (в браузере).
- Минусы:
  - Сложно использовать в мобильных приложениях.
  - Каждый запрос требует похода в хранилище сессий.
  - Проблемы с CORS и CSRF.

## Consequences

- **Положительные:** Масштабируемая, современная система безопасности, готовая к микросервисной архитектуре (сервисы могут валидировать JWT независимо по публичному ключу).
- **Отрицательные:** Необходимость реализации сервера авторизации (или использования готовых решений типа Keycloak/Auth0) и хранения Refresh токенов.
- **Риски:** Утечка секретного ключа для подписи JWT приведет к компрометации всей системы. Требуется автоматическая ротация ключей (JWKS).

## Migration / Evolution Path

На старте мы реализуем легковесный сервер авторизации (Identity Provider) внутри монолита. В будущем он может быть заменен на выделенное решение (например, Keycloak), при этом сервисы продолжат просто валидировать JWT, и для них переход будет прозрачным.
