# ADR-0012: Стратегия сквозной распределенной идемпотентности (Distributed Idempotency)

## Статус

Принято

## Контекст

В распределенной системе постоянно происходят сетевые сбои, повторные отправки запросов клиентами и повторная доставка сообщений из брокеров (At-Least-Once delivery). Это может привести к критическим ошибкам бизнес-логики: повторному списанию денег, дублированию заказов, повторному закрытию торгов. Требуется единый механизм предотвращения дублирования операций.

## Рассмотренные альтернативы

1. **Обработка «на удачу» без гарантий**: Недопустимо для финансовых и критичных логистических операций.
2. **Блокировка на уровне таблиц БД (Pessimistic Locking)**: Снижает пропускную способность системы, приводит к дедлокам при высоких нагрузках.
3. **Распределенное хранение состояния запросов + проверка в БД**: Использование заголовка `Idempotency-Key` от клиента, хранение ключей в Redis с блокировками (SETNX/Redlock) и финальная проверка уникальности на уровне СУБД.

## Решение

Мы выбираем **комплексную модель идемпотентности для API и потребителей событий**.

### Для REST/gRPC API:

- Клиент обязан передавать заголовок `Idempotency-Key` (UUID) для всех мутирующих запросов (POST/PUT/PATCH/DELETE).
- На уровне API Gateway или middleware сервиса проверяется наличие ключа в **Redis** (с помощью `SETNX`). Если запрос в обработке, возвращается статус `409 Conflict` (или блокируется до завершения). Если уже обработан — возвращается сохраненный ранее результат.
- Для гарантии на уровне хранения, в PostgreSQL создаются **unique constraints** на бизнес-сущности и/или таблицы лога транзакций.

### Для Consumer событий (Kafka):

- Применение **Idempotent Consumer pattern**.
- Каждое событие имеет уникальный `Event-ID`.
- Консьюмер перед обработкой или в рамках бизнес-транзакции проверяет наличие `Event-ID` в таблице `processed_events` (дедупликация).

### Обоснование

Идемпотентность — необходимое условие корректной работы систем с Transactional Outbox и нестабильными сетевыми соединениями. Многоуровневый подход (Redis для быстрой защиты + БД для 100% гарантии) обеспечивает и производительность, и безопасность.

## Последствия

### Положительные

- Защита от двойных списаний и дублирования бизнес-сущностей.
- Безопасное использование ретраев на клиентах и между микросервисами.

### Риски и их митигация

- **Риск**: Рост объема данных идемпотентности в Redis и PostgreSQL.
  **Митигация**: Установка TTL для ключей в Redis (например, 24 часа), партиционирование и регулярная очистка старых записей в таблице дедупликации БД.
- **Риск**: Неконсистентность при сбоях Redis.
  **Митигация**: Fallback на уникальные ограничения базы данных (PostgreSQL Unique Constraints).
