# ADR-0009: Архитектура высоконагруженного контура приема GPS-телеметрии

## Статус

Принято

## Контекст

Возникла необходимость обеспечить стабильный прием и обработку десятков тысяч точек геопозиции в секунду от телематических трекеров и мобильных устройств водителей. Эти устройства часто работают в условиях нестабильной связи, что приводит к пакетной отправке накопленных данных (spike-нагрузки). При этом критически важно не допустить деградации производительности основной базы данных платформы.

## Рассмотренные альтернативы

1. **Direct Write в PostgreSQL с PostGIS**: Простая архитектура, но не выдерживает высоких пиковых нагрузок и создает конкуренцию за ресурсы с транзакционными бизнес-запросами.
2. **Direct Write в TimescaleDB через REST API**: Лучше подходит для time-series данных, но остается риск перегрузки БД при массовом переподключении устройств и отсутствии буферизации.
3. **Выделенный Stateless Ingestion Gateway (Go/Rust) → Apache Kafka → Stream Processor → Redis (Current State) + TimescaleDB (Historical Track)**: Разделение приема данных и их долгосрочного хранения с использованием брокера сообщений.

## Решение

Мы выбираем **Выделенный Ingestion Gateway со стримингом через Kafka**.

### Обоснование

- **Изоляция spike-нагрузок**: Gateway принимает запросы асинхронно, отвечая сверхбыстро (`202 Accepted`), и складывает сырые данные в Kafka.
- **Буферизация**: Kafka выступает надежным буфером при сбоях или замедлении работы конечных баз данных.
- **Масштабируемость**: Stateless Gateway на Go/Rust легко горизонтально масштабируется.
- **Разделение хранения**: Актуальное состояние (Current State) обновляется в Redis для быстрого доступа, а исторические треки (Historical Track) асинхронно сохраняются в TimescaleDB для аналитики.

## Последствия

### Положительные

- Основная транзакционная БД (PostgreSQL) защищена от телематической нагрузки.
- Высокая доступность контура приема данных даже при недоступности хранилищ.
- Возможность подключения новых потребителей GPS-событий (например, сервиса геофенсинга) без изменения логики приема.

### Риски и их митигация

- **Риск**: Усложнение инфраструктуры за счет добавления Kafka и Stream Processors.
  **Митигация**: Использование управляемых (managed) сервисов Kafka и стандартизация деплоя через IaC.
- **Риск**: Задержка обработки (End-to-End Latency) между получением точки и её отображением на карте.
  **Митигация**: Разделение потоков на критичный (в Redis) и аналитический (в TimescaleDB), оптимизация партиционирования Kafka.
