# ADR-0006: Выбор архитектурного стиля внешнего и внутреннего API (REST + gRPC + Webhooks)

**Status**: Accepted

**Date**: 2023-10-25

## Context & Problem Statement

Система будет взаимодействовать с множеством клиентов: веб-портал (SPA), мобильное приложение для водителей, а также B2B интеграции со сторонними TMS (Транспортными системами) и ERP клиентов. Кроме того, внутренние модули (а в будущем микросервисы) также должны взаимодействовать друг с другом. Необходимо выбрать оптимальный набор протоколов взаимодействия.

## Decision Drivers

- Простота интеграции для внешних клиентов (открытость API).
- Высокая производительность и строгая типизация для межсервисного взаимодействия.
- Необходимость реактивного уведомления внешних систем о событиях в реальном времени.

## Considered Options

1. **Чистый REST/JSON для всего**: Стандартный HTTP/JSON.
2. **GraphQL для всего**: Единая точка входа для клиентских запросов.
3. **gRPC для всего**: Бинарный протокол на базе HTTP/2, высокая скорость, строгие контракты (Protobuf).
4. **Гибридный подход (REST + gRPC + Webhooks)**: Использование подходящего инструмента для каждой зоны.

## Decision Outcome

**Выбранный вариант:** Гибридный подход.

- **REST (JSON over HTTP)**: Для публичного API, SPA и B2B интеграций (OpenAPI/Swagger).
- **gRPC**: Для синхронного межсервисного взаимодействия (Service-to-Service) внутри платформы.
- **Webhooks**: Для отправки событий во внешние системы партнеров.
- **WebSocket / Server-Sent Events (SSE)**: Для real-time обновлений в SPA (нотификации, изменение статуса).

**Обоснование (Почему именно так?):**
Универсального решения ("серебряной пули") не существует. REST/JSON является универсальным языком интернета: любой клиент легко интегрируется с OpenAPI, это привычно и прозрачно для фронтенда и мобилок. Однако REST слишком "жирный" и медленный для внутренних коммуникаций между микросервисами, где критична скорость и строгая бинарная типизация — здесь gRPC вне конкуренции. Для B2B интеграции недостаточно только REST (polling ресурсов клиентом неэффективен), поэтому мы добавляем Webhooks, чтобы TMS партнеров получали push-уведомления об изменении статуса груза.

## Pros and Cons of the Options

### Гибридный подход

- Плюсы:
  - Идеальное соответствие инструмента задаче.
  - Дружелюбный API для партнеров (REST/Webhooks).
  - Максимальная производительность внутри кластера (gRPC).
- Минусы:
  - Увеличивается когнитивная нагрузка на разработчиков (нужно знать OpenAPI и Protobuf).
  - Необходимость поддерживать разные слои транспортных адаптеров.

### Чистый REST

- Плюсы: Простота и единообразие.
- Минусы: Отсутствие строгих гарантий контрактов (OpenAPI часто рассинхронизируется с кодом), медленная сериализация JSON для внутренних вызовов.

### GraphQL

- Плюсы: Клиент сам выбирает нужные данные, решает проблему over-fetching.
- Минусы: Сложность в обеспечении безопасности, кэшировании и проблемах N+1 при разработке API. Избыточен для большинства наших B2B сценариев.

## Consequences

- **Положительные:** Мы обеспечим отличный Developer Experience для внешних партнеров и высокую производительность для бэкенда.
- **Отрицательные:** Нужно настроить процесс генерации кода для gRPC (protoc) и генерации Swagger-документации.

## Migration / Evolution Path

В рамках Модульного Монолита на старте синхронное межсервисное взаимодействие будет осуществляться вызовом методов интерфейсов in-memory. При выносе модуля в микросервис, этот интерфейс будет заменен на gRPC-клиент. Публичный REST API и Webhooks реализуются с первого дня работы платформы.
