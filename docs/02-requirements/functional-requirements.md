# Функциональные требования

Данный документ содержит полный структурированный каталог функциональных требований к платформе автомобильных грузоперевозок. Требования сгруппированы по Bounded Contexts и описывают функциональность для всего бизнес-цикла от публикации груза до проведения расчетов.

## FR-IAM: Identity, Access & Organization Management

### FR-IAM-001: Регистрация и верификация организации

- **Описание**: Система должна позволять грузоотправителям и перевозчикам регистрировать свои компании с последующей верификацией профиля.
- **Приоритет**: Must Have
- **Связанные акторы**: Shipper, Carrier, Admin
- **Предусловия (Pre-conditions)**: Пользователь не авторизован в системе.
- **Основной сценарий (Main Flow)**:
  1. Пользователь вводит ИНН/ОГРН компании.
  2. Система автоматически заполняет карточку организации из открытых реестров.
  3. Пользователь загружает уставные документы.
  4. Администратор или автоматизированная служба безопасности проверяет данные и одобряет/отклоняет регистрацию.
- **Критерии приёмки (Acceptance Criteria)**:
  - Given: Пользователь вводит корректный ИНН.
  - When: Нажимает "Далее".
  - Then: Данные о компании подтягиваются автоматически.
  - Given: Заявка на верификацию отправлена.
  - Then: Статус организации меняется на "На проверке". Профиль не может выполнять значимые операции до получения статуса "Верифицирован".
- **Связанные сущности и события**: Organization, User. События: `OrganizationRegistered`, `OrganizationVerified`.

## FR-MKT: Load Board, Truck Board, Tenders & Private Marketplace

### FR-MKT-001: Публикация груза (Load Board)

- **Описание**: Грузоотправитель должен иметь возможность разместить груз на открытой площадке или приватном маркетплейсе с указанием всех необходимых свойств (температурный режим, ADR, габариты, окна погрузки/выгрузки, условия оплаты).
- **Приоритет**: Must Have
- **Связанные акторы**: Shipper
- **Предусловия (Pre-conditions)**: Пользователь авторизован и верифицирован как Грузоотправитель.
- **Основной сценарий (Main Flow)**:
  1. Пользователь нажимает "Добавить груз".
  2. Заполняет маршрут (точки А и Б, дата и окна погрузки/выгрузки).
  3. Указывает характеристики груза: вес, объем, температурный режим, ADR, габариты.
  4. Задает условия оплаты и ставку.
  5. Выбирает видимость: публичная биржа или приватный пул перевозчиков.
  6. Публикует груз.
- **Критерии приёмки (Acceptance Criteria)**:
  - Форма не отправляется без указания обязательных полей (маршрут, вес, тип кузова).
  - При выборе ADR система требует указать класс опасности.
  - Груз отображается в ленте поиска для перевозчиков, соответствующих критериям видимости.
- **Связанные сущности и события**: Load, Location. События: `LoadPublished`.

### FR-MKT-002: Публикация свободной машины (Truck Board)

- **Описание**: Перевозчик должен иметь возможность заявить о доступности транспортного средства в определенной локации и радиусе.
- **Приоритет**: Must Have
- **Связанные акторы**: Carrier, Dispatcher
- **Предусловия (Pre-conditions)**: Пользователь авторизован как Перевозчик или Диспетчер.
- **Основной сценарий (Main Flow)**:
  1. Пользователь выбирает ТС из своего автопарка.
  2. Указывает тип кузова, грузоподъемность.
  3. Задает текущую или планируемую локацию, дату доступности и радиус подачи.
  4. Публикует доступность.
- **Критерии приёмки (Acceptance Criteria)**:
  - Перевозчик может указать радиус подачи машины в километрах.
  - Доступная машина отображается грузоотправителям при поиске транспорта в данном радиусе.
- **Связанные сущности и события**: Truck Availability. События: `TruckPublished`.

### FR-MKT-003: Закрытые торги/тендеры и приватные площадки

- **Описание**: Грузоотправитель может проводить торги на понижение/повышение или размещать грузы только для доверенных пулов перевозчиков.
- **Приоритет**: Should Have
- **Связанные акторы**: Shipper, Carrier
- **Предусловия (Pre-conditions)**: Создан пул доверенных перевозчиков (Private Fleet).
- **Основной сценарий (Main Flow)**:
  1. При публикации груза Грузоотправитель выбирает тип "Тендер" или "Приватная площадка".
  2. Выбирает пул перевозчиков, которым будет доступна заявка.
  3. Устанавливает начальную ставку и шаг торгов (для тендера).
  4. Перевозчики из пула получают уведомления и делают ставки.
  5. По истечении времени тендера Грузоотправитель выбирает победителя или система делает это автоматически.
- **Критерии приёмки (Acceptance Criteria)**:
  - Перевозчики не из пула не видят приватные грузы в поиске.
  - Ставки в тендере обновляются в реальном времени у всех участников.
- **Связанные сущности и события**: Tender, Bid, PrivatePool. События: `TenderCreated`, `BidPlaced`, `TenderClosed`.

### FR-MKT-004: Автоматическая деактивация груза

- **Описание**: Система должна автоматически снимать груз с публикации при наступлении определенных условий (истечение срока или назначение перевозчика).
- **Приоритет**: Must Have
- **Связанные акторы**: System
- **Предусловия (Pre-conditions)**: Груз находится в статусе "Активен" или "В поиске".
- **Основной сценарий (Main Flow)**:
  1. Система периодически проверяет сроки действия грузов (окна погрузки).
  2. Если время погрузки истекло или грузу назначен перевозчик, система меняет статус публикации на "Архив" или "Назначен" и убирает из выдачи.
- **Критерии приёмки (Acceptance Criteria)**:
  - Груз пропадает из выдачи для новых перевозчиков мгновенно после подтверждения назначения.
  - Если дата погрузки наступила, а перевозчик не найден, груз автоматически деактивируется, автор получает уведомление.
- **Связанные сущности и события**: Load. События: `LoadDeactivated`.

## FR-MCH: Matching Engine, Counter-offers & Negotiation

### FR-MCH-001: Офферы и встречные предложения

- **Описание**: Пользователи должны иметь возможность делать встречные предложения по цене и условиям перевозки, с возможностью установки срока действия оффера.
- **Приоритет**: Must Have
- **Связанные акторы**: Shipper, Carrier, Dispatcher
- **Предусловия (Pre-conditions)**: Опубликован груз со статусом "Открыт для предложений".
- **Основной сценарий (Main Flow)**:
  1. Перевозчик просматривает груз и нажимает "Предложить свои условия".
  2. Вводит свою ставку, возможные даты и срок действия оффера.
  3. Грузоотправитель получает уведомление и может Принять, Отклонить или Сделать встречный оффер.
  4. Процесс повторяется до достижения согласия или истечения срока оффера.
- **Критерии приёмки (Acceptance Criteria)**:
  - Оффер автоматически отменяется, если срок его действия истек.
  - Стороны не могут изменять оффер после того, как другая сторона его приняла.
- **Связанные сущности и события**: Offer. События: `OfferSubmitted`, `OfferCountered`, `OfferAccepted`, `OfferExpired`.

### FR-MCH-002: Чат по офферу и фиксация договоренности

- **Описание**: Для каждого оффера должен быть доступен изолированный чат между Грузоотправителем и Перевозчиком с возможностью фиксации финальных условий.
- **Приоритет**: Should Have
- **Связанные акторы**: Shipper, Carrier
- **Предусловия (Pre-conditions)**: Создан активный оффер.
- **Основной сценарий (Main Flow)**:
  1. Стороны переписываются в чате, привязанном к конкретному офферу.
  2. В интерфейсе чата доступна кнопка "Зафиксировать условия".
  3. При нажатии генерируется финальный оффер, который требует подтверждения второй стороной.
- **Критерии приёмки (Acceptance Criteria)**:
  - История чата сохраняется бессрочно и привязана к сущности оффера.
  - Подтвержденные в чате условия автоматически конвертируются в транспортный заказ.
- **Связанные сущности и события**: ChatMessage, Offer. События: `MessageSent`, `TermsFixed`.

## FR-ORD: Transport Orders, Multi-stop Shipments & Assignment

### FR-ORD-001: Создание транспортного заказа из согласованного оффера

- **Описание**: Принятый оффер должен автоматически конвертироваться в юридически значимый транспортный заказ.
- **Приоритет**: Must Have
- **Связанные акторы**: System, Shipper, Carrier
- **Предусловия (Pre-conditions)**: Оффер перешел в статус "Принят".
- **Основной сценарий (Main Flow)**:
  1. Система формирует сущность Order на основе данных Load и Offer.
  2. Блокирует возможность изменения маршрута и стоимости без дополнительного согласования.
  3. Переводит статус груза в "Исполняется".
- **Критерии приёмки (Acceptance Criteria)**:
  - Транспортный заказ содержит все условия из исходного груза и финального оффера.
  - Генерируется печатная форма заявки в формате PDF.
- **Связанные сущности и события**: Order. События: `OrderCreated`.

### FR-ORD-002: Назначение ТС и водителя с валидацией

- **Описание**: Перевозчик должен назначить конкретное транспортное средство и водителя на заказ с обязательной проверкой их прав, пропусков и доступности.
- **Приоритет**: Must Have
- **Связанные акторы**: Carrier, Dispatcher
- **Предусловия (Pre-conditions)**: Создан транспортный заказ.
- **Основной сценарий (Main Flow)**:
  1. Перевозчик выбирает водителя и ТС/прицеп из своего справочника.
  2. Система проверяет, не назначен ли водитель на другой пересекающийся по времени рейс.
  3. Проверяется срок действия ВУ водителя и СТС машины.
  4. При успешной проверке данные прикрепляются к заказу и отправляются Грузоотправителю.
- **Критерии приёмки (Acceptance Criteria)**:
  - Система блокирует назначение водителя с просроченным ВУ.
  - Система выдает предупреждение (или блокирует) при попытке назначить ТС, уже занятое в эти даты.
- **Связанные сущности и события**: Order, Vehicle, Driver. События: `ResourceAssigned`.

### FR-ORD-003: Маршрутизация с несколькими точками (Multi-stop)

- **Описание**: Поддержка заказов со сложными маршрутами, включающими несколько точек погрузки и выгрузки.
- **Приоритет**: Must Have
- **Связанные акторы**: Shipper, System
- **Предусловия (Pre-conditions)**: Создание или редактирование груза/заказа.
- **Основной сценарий (Main Flow)**:
  1. Грузоотправитель добавляет 3 и более точек маршрута (например: А - погрузка, Б - догруз, В - выгрузка 1, Г - выгрузка 2).
  2. Для каждой точки задается своя дата/окно, вес и тип операции.
  3. Система рассчитывает общую протяженность маршрута.
- **Критерии приёмки (Acceptance Criteria)**:
  - Система валидирует последовательность точек (сначала минимум 1 погрузка, затем выгрузки).
  - Учет общего веса груза не должен превышать грузоподъемность на любом отрезке маршрута.
- **Связанные сущности и события**: RouteStop. События: `StopsUpdated`.

## FR-EXE: Execution Lifecycle, Status Tracking & Exceptions

### FR-EXE-001: Изменение статусов исполнения перевозки

- **Описание**: Трекинг жизненного цикла заказа с жестко заданным стейт-стейт-машиной статусов (Назначен -> На погрузке -> В пути -> На выгрузке -> Завершен).
- **Приоритет**: Must Have
- **Связанные акторы**: Driver, Dispatcher
- **Предусловия (Pre-conditions)**: Транспортный заказ в работе, назначены водитель и ТС.
- **Основной сценарий (Main Flow)**:
  1. Водитель в мобильном приложении нажимает "Прибыл на погрузку".
  2. Статус заказа меняется, отправляется уведомление Грузоотправителю.
  3. Процесс повторяется для всех ключевых точек маршрута.
- **Критерии приёмки (Acceptance Criteria)**:
  - Водитель не может переключить статус на "В пути", минуя "На погрузке".
  - Статусы могут меняться автоматически на основе гео-данных (FR-TRK-002).
- **Связанные сущности и события**: OrderStatus. События: `OrderStatusChanged`.

### FR-EXE-002: Смена машины/водителя на маршруте

- **Описание**: При поломке или других обстоятельствах Перевозчик может заменить ТС/водителя, что должно фиксироваться в системе с уведомлением заказчика и аудитом.
- **Приоритет**: Must Have
- **Связанные акторы**: Carrier, Dispatcher, Shipper
- **Предусловия (Pre-conditions)**: Заказ находится в статусе исполнения ("В пути" и т.д.).
- **Основной сценарий (Main Flow)**:
  1. Перевозчик инициирует процесс замены ТС/водителя.
  2. Указывает причину замены.
  3. Выбирает новые ресурсы из справочника.
  4. Грузоотправитель получает уведомление о смене ресурсов.
  5. Запись о смене навсегда сохраняется в логе аудита заказа.
- **Критерии приёмки (Acceptance Criteria)**:
  - Все изменения ресурсов после создания заказа логируются.
  - Новые ресурсы проходят валидацию так же, как при первоначальном назначении (FR-ORD-002).
- **Связанные сущности и события**: Order, ResourceChangeRequest. События: `ResourceChanged`.

### FR-EXE-003: Фиксация нештатных ситуаций (Exceptions)

- **Описание**: Возможность фиксации инцидентов (опоздание, ДТП, отказ, перегруз, расхождение номенклатуры) с привязкой к заказу.
- **Приоритет**: Must Have
- **Связанные акторы**: Driver, Dispatcher, Shipper
- **Предусловия (Pre-conditions)**: Заказ находится в активном статусе.
- **Основной сценарий (Main Flow)**:
  1. Водитель или Диспетчер создает Инцидент (Exception) к текущему заказу.
  2. Выбирает тип инцидента (например, "ДТП").
  3. Прикрепляет описание, фото или документы.
  4. Грузоотправитель моментально оповещается о проблеме.
- **Критерии приёмки (Acceptance Criteria)**:
  - Инцидент отображается на дашбордах обеих сторон.
  - Заказ может быть заблокирован для завершения до разрешения инцидента.
- **Связанные сущности и события**: OrderException. События: `ExceptionRaised`, `ExceptionResolved`.

## FR-TRK: GPS Telematics, Geofencing & ETA Calculation

### FR-TRK-001: Прием телематики с высокой частотой

- **Описание**: Система должна принимать и обрабатывать GPS-координаты от мобильного приложения или внешних телематических провайдеров с частотой от 10 секунд до 1 минуты.
- **Приоритет**: Must Have
- **Связанные акторы**: External System, Driver App
- **Предусловия (Pre-conditions)**: Заказ находится в стадии исполнения, трекинг активен.
- **Основной сценарий (Main Flow)**:
  1. Источник (приложение или API провайдера) отправляет координаты (Lat/Lon, Speed, Timestamp).
  2. Система сохраняет точку маршрута в базу данных трекинга.
  3. Текущее местоположение обновляется на карте интерфейса в реальном времени.
- **Критерии приёмки (Acceptance Criteria)**:
  - Система способна обрабатывать поток координат без существенных задержек.
  - Координаты хранятся для последующего воспроизведения маршрута (Track History).
- **Связанные сущности и события**: GpsPing. События: `LocationUpdated`.

### FR-TRK-002: Детекция входа/выхода из геозон

- **Описание**: Автоматическое определение факта прибытия/убытия ТС в зону погрузки/разгрузки (Geofencing).
- **Приоритет**: Should Have
- **Связанные акторы**: System
- **Предусловия (Pre-conditions)**: Вокруг точек маршрута созданы виртуальные геозоны (например, радиус 500 метров).
- **Основной сценарий (Main Flow)**:
  1. При поступлении новой GPS-координаты система проверяет пересечение с геозоной точки маршрута.
  2. Если ТС входит в зону погрузки, автоматически меняется статус на "Прибыл на погрузку" (если не переключено вручную).
  3. Генерируется событие входа/выхода для расчета времени простоя.
- **Критерии приёмки (Acceptance Criteria)**:
  - Ложные срабатывания фильтруются (требуется нахождение в зоне минимум X минут).
  - Автоматическая смена статуса отражается в аудите как системная.
- **Связанные сущности и события**: GeofenceEvent. События: `GeofenceEntered`, `GeofenceExited`.

### FR-TRK-003: Расчет задержек и динамического ETA

- **Описание**: Система должна вычислять предполагаемое время прибытия (ETA) на основе текущей локации, скорости и дорожной обстановки.
- **Приоритет**: Should Have
- **Связанные акторы**: System
- **Предусловия (Pre-conditions)**: Поступают регулярные GPS-данные.
- **Основной сценарий (Main Flow)**:
  1. Система периодически пересчитывает время в пути до следующей точки.
  2. Если ETA превышает окно прибытия более чем на заданный порог, генерируется предупреждение о возможном опоздании (Risk of Delay).
- **Критерии приёмки (Acceptance Criteria)**:
  - ETA обновляется минимум раз в 15 минут.
  - Грузоотправитель видит актуальный прогноз прибытия груза в интерфейсе.
- **Связанные сущности и события**: RouteETA. События: `EtaUpdated`, `DelayRiskDetected`.

## FR-DOC: Electronic Documents, eCMR, Photo PoD & E-Signature

### FR-DOC-001: Загрузка и распознавание документов (Photo PoD)

- **Описание**: Водитель или перевозчик должен иметь возможность загрузить фото товаросопроводительных документов с автоматическим распознаванием и фиксацией повреждений.
- **Приоритет**: Must Have
- **Связанные акторы**: Driver, Carrier, System
- **Предусловия (Pre-conditions)**: Груз доставлен (статус "На выгрузке" или "Завершен").
- **Основной сценарий (Main Flow)**:
  1. Водитель делает фото подписанной накладной через мобильное приложение.
  2. Система производит OCR, сверяя номера и печати.
  3. При наличии повреждений груза загружаются фото-доказательства (Photo PoD).
  4. Документы прикрепляются к заказу.
- **Критерии приёмки (Acceptance Criteria)**:
  - Фотографии сжимаются, но остаются читаемыми.
  - Пользователь может вручную верифицировать распознанные данные.
- **Связанные сущности и события**: Document, PhotoPoD. События: `DocumentUploaded`, `PodVerified`.

### FR-DOC-002: Формирование и подписание eCMR

- **Описание**: Платформа должна поддерживать создание электронных транспортных накладных (eCMR/ЭТрН) и их подписание электронными подписями всех участников перевозки.
- **Приоритет**: Should Have
- **Связанные акторы**: Shipper, Driver, Consignee, System
- **Предусловия (Pre-conditions)**: Интеграция с провайдером ЭДО (Электронного документооборота).
- **Основной сценарий (Main Flow)**:
  1. При создании заказа формируется XML/PDF проект eCMR.
  2. Грузоотправитель подписывает титул УКЭП (усиленной квалифицированной ЭП).
  3. Водитель подписывает ПЭП (простой ЭП) или УНЭП в приложении.
  4. Грузополучатель подписывает титул приемки.
- **Критерии приёмки (Acceptance Criteria)**:
  - Юридическая значимость документа обеспечивается согласно законодательству.
  - Файлы подписей (sig) хранятся вместе с документом и доступны для скачивания.
- **Связанные сущности и события**: EcmrDocument, Signature. События: `EcmrSignedByShipper`, `EcmrCompleted`.

## FR-FIN: Pricing, Invoicing, Platform Fee, Factoring & Escrow

### FR-FIN-001: Выставление счетов и расчет комиссионного вознаграждения

- **Описание**: Система должна автоматически формировать счета на оплату услуг перевозки и рассчитывать комиссию платформы.
- **Приоритет**: Must Have
- **Связанные акторы**: Admin, System, Carrier, Shipper
- **Предусловия (Pre-conditions)**: Заказ завершен, оригиналы документов (или eCMR) получены и проверены.
- **Основной сценарий (Main Flow)**:
  1. Перевозчик нажимает "Сформировать счет".
  2. Система генерирует счет-фактуру/акт на основе тарифа заказа, добавляя возможные простои (accessorials).
  3. Параллельно формируется счет на комиссию платформы в адрес Перевозчика (или Грузоотправителя, согласно тарифному плану).
- **Критерии приёмки (Acceptance Criteria)**:
  - Автоматический расчет простоев на основе данных гео-трекинга (FR-TRK-002).
  - Счета можно выгрузить в PDF или передать по API в ERP/Бухгалтерию.
- **Связанные сущности и события**: Invoice, Fee. События: `InvoiceGenerated`, `FeeCalculated`.

## FR-TRT: Verification, Reputation Scoring, Ratings & Blacklists

### FR-TRT-001: Скоринг благонадежности и проверка контрагентов

- **Описание**: Автоматическая проверка ИНН/ОГРН по государственным реестрам и расчет рейтинга благонадежности для предотвращения мошенничества.
- **Приоритет**: Must Have
- **Связанные акторы**: System, Admin
- **Предусловия (Pre-conditions)**: Регистрация новой организации или периодический аудит.
- **Основной сценарий (Main Flow)**:
  1. Система по API запрашивает данные из ЕГРЮЛ, реестров ФНС, ФССП, арбитражных судов.
  2. На основе собранных факторов (возраст компании, суды, долги) рассчитывается Score.
  3. Если Score ниже порога, аккаунт блокируется или отправляется на ручную проверку.
- **Критерии приёмки (Acceptance Criteria)**:
  - Признаки массового директора или банкротства немедленно понижают статус аккаунта.
  - Пользователи видят индикатор "Надежность" (зеленый/желтый/красный) в профилях друг друга.
- **Связанные сущности и события**: OrganizationScore, CheckResult. События: `ScoringUpdated`, `AccountSuspended`.

### FR-TRT-002: Взаимные отзывы и рейтинги, ЧС

- **Описание**: После каждой перевозки стороны могут оставить друг другу отзыв и оценку. Возможность заносить контрагентов в приватный черный список (ЧС).
- **Приоритет**: Should Have
- **Связанные акторы**: Shipper, Carrier
- **Предусловия (Pre-conditions)**: Транспортный заказ завершен.
- **Основной сценарий (Main Flow)**:
  1. Система просит участников оценить перевозку от 1 до 5 звезд.
  2. Отзывы формируют средний рейтинг компании.
  3. Любая компания может добавить другую в свой ЧС, чтобы больше не видеть её грузы/машины.
- **Критерии приёмки (Acceptance Criteria)**:
  - Отзыв можно оставить только после подтвержденной сделки (анти-спам).
  - В случае попадания в ЧС, алгоритмы Matching (FR-MCH) игнорируют этого контрагента.
- **Связанные сущности и события**: Review, Rating, Blacklist. События: `ReviewLeft`, `BlacklistUpdated`.

### FR-TRT-003: Двухфакторное подтверждение значимых операций

- **Описание**: Для критических действий (смена реквизитов, смена водителя, снятие средств) должна применяться 2FA (SMS/Email/Authenticator).
- **Приоритет**: Must Have
- **Связанные акторы**: User
- **Предусловия (Pre-conditions)**: Настроена 2FA в профиле.
- **Основной сценарий (Main Flow)**:
  1. Пользователь инициирует смену банковских реквизитов.
  2. Система запрашивает одноразовый код.
  3. После ввода корректного кода операция выполняется.
- **Критерии приёмки (Acceptance Criteria)**:
  - Без ввода кода реквизиты не изменяются.
  - Попытки неверного ввода кода логируются для выявления брутфорса.
- **Связанные сущности и события**: SecurityAction, TwoFactorChallenge. События: `OtpRequested`, `ActionVerified`.

## FR-COM: Messenger, System & Multi-channel Notifications

### FR-COM-001: Многоканальные оповещения и уведомления

- **Описание**: Отправка уведомлений о событиях в системе (новые грузы, смена статуса заказа, новые сообщения) через различные каналы: Push, SMS, Email, In-App.
- **Приоритет**: Must Have
- **Связанные акторы**: System, User
- **Предусловия (Pre-conditions)**: Пользователь настроил предпочтения уведомлений.
- **Основной сценарий (Main Flow)**:
  1. Генерируется доменное событие (например, `OrderCreated`).
  2. Модуль уведомлений определяет подписанных пользователей и их настройки.
  3. Формируется шаблон сообщения и отправляется в нужные каналы.
- **Критерии приёмки (Acceptance Criteria)**:
  - Пользователь может отказаться от Email рассылок, но обязательные системные уведомления доставляются In-App.
  - Push-уведомления доставляются в мобильное приложение водителя с задержкой не более 5 секунд.
- **Связанные сущности и события**: Notification, NotificationPreference. События: `NotificationSent`.

## FR-INT: External APIs, Webhooks & EDI/TMS/ERP Integration

### FR-INT-001: Внешние API, Webhooks и интеграция с ERP

- **Описание**: Платформа должна предоставлять REST/GraphQL API для интеграции с внешними TMS (Transport Management Systems) и ERP системами грузоотправителей.
- **Приоритет**: Should Have
- **Связанные акторы**: External System, Admin
- **Предусловия (Pre-conditions)**: У клиента сгенерирован API Key.
- **Основной сценарий (Main Flow)**:
  1. Внешняя ERP создает заявку на перевозку через API POST запрос.
  2. Платформа регистрирует груз (FR-MKT-001) и возвращает ID.
  3. При смене статуса заказа платформа отправляет Webhook на сервер клиента.
- **Критерии приёмки (Acceptance Criteria)**:
  - API защищено с помощью OAuth2 или Bearer токенов.
  - Все изменения статусов дублируются через Webhooks с поддержкой retry-логики в случае недоступности эндпоинта клиента.
- **Связанные сущности и события**: ApiKey, WebhookSubscription. События: `WebhookFired`.
