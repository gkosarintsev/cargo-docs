# Доступность (Availability)

Платформа должна обеспечивать непрерывность бизнес-процессов. В данном документе определены целевые показатели уровня обслуживания и стратегии контролируемой деградации.

## 1. SLA/SLO/SLI матрица по сервисам

Для ключевых компонентов платформы установлены следующие требования к доступности:

| Сервис / Подсистема              | Доступность (SLA/SLO) | Критерии производительности (SLI)               |
| :------------------------------- | :-------------------- | :---------------------------------------------- |
| **Marketplace Search**           | **99.9%**             | p95 < 200ms, p99 < 800ms                        |
| **Order Creation & Core API**    | **99.95%**            | p95 < 150ms                                     |
| **GPS Ingestion Gateway**        | **99.99%**            | Zero packet drop на входе                       |
| **Dispatcher Live Tracking Map** | **99.5%**             | Задержка отображения < 3 сек                    |
| **Document Signing & EDO**       | **99.9%**             | Успешная валидация подписи / создание документа |

## 2. Graceful Degradation (Режимы контролируемой деградации)

В случае отказа некритичных подсистем система должна переходить в режим ограниченной функциональности, сохраняя работоспособность ключевых процессов.

### Что происходит при отказе OpenSearch (поисковый кластер)

- **Поведение:** При сбоях OpenSearch/Elasticsearch система переключается на использование базового кэшированного фильтра в реляционной БД (PostgreSQL), либо отображает read-only сообщение "Расширенный поиск временно недоступен", оставляя возможность работать с уже созданными активными заказами.

### Что происходит при перегрузке GPS шлюза

- **Поведение:** В случае пиковых нагрузок происходит буферизация телеметрии на стороне мобильных клиентов с использованием экспоненциальной задержки. На уровне Ingress шлюза может выполняться сброс второстепенных телеметрических полей или пакетов без изменения ключевых статусов для снижения нагрузки на очередь Kafka.

### Поведение системы при сбоях внешних SMS/Email/Push провайдеров

- **Поведение:** Отложенная отправка через асинхронные очереди (Retry Queue). В случаях, критичных для безопасности (аутентификация), платформа предлагает fallback на альтернативные каналы (отправка кода на Email при недоступности SMS) или предоставляет использование сгенерированных резервных кодов.
