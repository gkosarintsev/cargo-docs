# Версионирование API (API Versioning)

> **Раздел:** 14-api  
> **Версия документа:** 1.0  
> **Статус:** Действующий стандарт  
> **Связанные документы:** [api-guidelines.md](api-guidelines.md)

---

## 1. Стратегия версионирования

Платформа CargoPlus использует **URL Path Versioning** — версия API указывается как часть пути URI:

```
/api/v{major}/...
```

**Примеры:**

```
/api/v1/loads
/api/v2/loads
/api/v1/transport-orders
```

### Обоснование выбора

| Подход                     | Преимущество                         | Выбран |
| -------------------------- | ------------------------------------ | :----: |
| URL Path (`/api/v1/`)      | Явность, простота отладки, cacheable |   ✅   |
| Header (`API-Version: 1`)  | Чистые URL                           |   ❌   |
| Query param (`?version=1`) | Неоднозначность кэширования          |   ❌   |
| Content Negotiation        | Сложность клиентов                   |   ❌   |

---

## 2. Схема версий

```
/api/v{N}/...
```

- Версия инкрементируется только при **breaking changes** (ломающих изменениях).
- Одновременно поддерживается не более **2 major-версий**.
- Версия `v1` — текущая production-версия.
- Версия `v0` — зарезервирована для внутреннего использования и нестабильных экспериментов (не документируется публично).

---

## 3. Классификация изменений: Breaking vs Non-Breaking

### 3.1 Non-Breaking Changes (без увеличения версии)

Следующие изменения **не требуют** новой версии API:

| Тип изменения                                           | Пример                                      |
| ------------------------------------------------------- | ------------------------------------------- |
| Добавление нового поля в ответ                          | `"estimated_delivery_at": "2024-03-16T..."` |
| Добавление нового необязательного параметра запроса     | `?include_archived=true`                    |
| Добавление нового эндпоинта                             | `GET /api/v1/loads/{id}/timeline`           |
| Добавление нового статус-кода (которого раньше не было) | `202 Accepted` для нового async flow        |
| Расширение enum (добавление нового значения)            | `status: "awaiting_documents"`              |
| Улучшение сообщений об ошибках                          | Более подробный `detail`                    |

> **Правило:** Клиенты обязаны игнорировать неизвестные поля в ответе (толерантное чтение — Postel's Law).

### 3.2 Breaking Changes (требуют новой major-версии)

| Тип изменения                          | Пример                                                |
| -------------------------------------- | ----------------------------------------------------- |
| Удаление поля из ответа                | Удаление `carrier_rating`                             |
| Переименование поля                    | `price` → `price_amount`                              |
| Изменение типа поля                    | `price: string` → `price: integer`                    |
| Изменение структуры ответа             | Перенос данных в sub-объект                           |
| Удаление эндпоинта                     | `DELETE /api/v1/loads/{id}/apply`                     |
| Изменение семантики метода             | `POST /loads` теперь создаёт черновик, а не публикует |
| Удаление значения из enum              | Удаление статуса `"draft"`                            |
| Добавление обязательного поля в запрос | Новое обязательное поле `cargo_type`                  |

## 4. Политика устаревания (Deprecation Policy)

### 4.1 Жизненный цикл версии

```
Stable → Deprecated → Sunset
  │           │           │
  │     min 6 months      │
  │<──────────────────────>│
```

1. **Stable** — версия активно используется и поддерживается.
2. **Deprecated** — версия устаревает, поддерживается, но не рекомендуется.
3. **Sunset** — версия отключается, запросы отклоняются с `410 Gone`.

### 4.2 Стандартные заголовки Deprecation

При работе с устаревшей версией к каждому ответу добавляются заголовки:

```http
Deprecation: @1710496800
Sunset: Sat, 01 Mar 2025 00:00:00 GMT
Link: <https://api.cargo.platform/api/v2/loads>; rel="successor-version"
```

| Заголовок     | Значение                        | Описание                               |
| ------------- | ------------------------------- | -------------------------------------- |
| `Deprecation` | `@<unix_timestamp>`             | Дата объявления устаревания (RFC 8594) |
| `Sunset`      | `<HTTP-date>`                   | Дата отключения версии (RFC 8594)      |
| `Link`        | URL с `rel="successor-version"` | Ссылка на актуальную версию            |

### 4.3 Регламент вывода из эксплуатации

1. **За 6 месяцев до отключения:** Объявление устаревания, добавление заголовков `Deprecation` и `Sunset` ко всем ответам.
2. **За 3 месяца:** Email-уведомление всем разработчикам, зарегистрировавшим API Key и активно использующим устаревшую версию.
3. **За 1 месяц:** Баннер в панели разработчика, напоминание в changelog.
4. **За 1 неделю:** Предупредительное сообщение в теле ответа (`meta.deprecation_warning`).
5. **День X:** Версия отключается. Ответ: `410 Gone`.

```json
// 410 Gone — попытка обратиться к отключённой версии
{
  "type": "https://api.cargo.platform/errors/api-version-sunset",
  "title": "Версия API отключена",
  "status": 410,
  "detail": "API v1 отключён 01.03.2025. Используйте API v2.",
  "error_code": "API_VERSION_SUNSET",
  "successor_url": "https://api.cargo.platform/api/v2/"
}
```

## 5. Правила разработки новых версий

### 5.1 Параллельная поддержка

- Максимум 2 major-версии существуют одновременно.
- При выпуске `v3` начинается deprecation `v1` (не `v2`).
- Обе версии обслуживаются теми же микросервисами; маршрутизация — через API Gateway.

### 5.2 Документирование изменений

- Changelog ведётся в `/docs/14-api/CHANGELOG.md`.
- Каждая новая версия сопровождается Migration Guide (`/docs/14-api/migration-v1-v2.md`).

### 5.3 Бета-версии

- Нестабильные экспериментальные эндпоинты помечаются заголовком: `X-API-Beta: true`.
- Бета-эндпоинты могут меняться без предупреждения и не считаются breaking change.
