# Ограничение частоты запросов (Rate Limiting)

> **Раздел:** 14-api  
> **Версия документа:** 1.0  
> **Статус:** Действующий стандарт  
> **Связанные документы:** [api-guidelines.md](api-guidelines.md), [errors.md](errors.md), [authentication.md](authentication.md)

---

## 1. Назначение

Rate Limiting защищает платформу от злоупотреблений, обеспечивает равномерную нагрузку на сервисы и гарантирует качество обслуживания всем клиентам. Ограничения применяются на уровне API Gateway до передачи запроса бэкенд-сервисам.

---

## 2. Алгоритм ограничения

Платформа использует алгоритм **Token Bucket** (с элементами Leaky Bucket для сглаживания пиков):

```
Token Bucket:
  - Каждый клиент имеет "ведро" токенов максимальной ёмкостью = лимит/мин
  - Токены добавляются с постоянной скоростью (rate = лимит / 60 токенов/сек)
  - Каждый запрос потребляет 1 токен
  - Если токенов нет → ответ 429 Too Many Requests
```

**Хранилище состояния:** Redis (атомарные операции INCR + EXPIRE, Lua-скрипт для атомарности).

**Ключ в Redis:**

```
rate_limit:{tier}:{identifier}:{window}
```

Например:

```
rate_limit:authenticated:usr_abc123:2024031510
rate_limit:api_key:key_xyz789:2024031510
```

## 3. Уровни ограничений (Tiers)

### 3.1 Публичный поиск (Unauthenticated)

Применяется к эндпоинтам поиска грузов и транспорта без аутентификации.

| Параметр        | Значение                                                                |
| --------------- | ----------------------------------------------------------------------- |
| Идентификатор   | IP-адрес клиента                                                        |
| Лимит           | **100 запросов / минута**                                               |
| Burst (пиковый) | 20 запросов одновременно                                                |
| Применяется к   | `GET /api/v1/loads` (публичный), `GET /api/v1/truck-offers` (публичный) |

### 3.2 Аутентифицированный пользователь (JWT)

Применяется ко всем запросам с валидным JWT токеном.

| Параметр        | Значение                  |
| --------------- | ------------------------- |
| Идентификатор   | `sub` (user ID) из JWT    |
| Лимит           | **600 запросов / минута** |
| Burst (пиковый) | 100 запросов одновременно |
| Применяется к   | Все защищённые эндпоинты  |

### 3.3 TMS/ERP API Integration (API Key)

Применяется к запросам с B2B API Key для машинных интеграций.

| Параметр        | Значение                         |
| --------------- | -------------------------------- |
| Идентификатор   | `key_id` API Key                 |
| Лимит           | **3000 запросов / минута**       |
| Burst (пиковый) | 500 запросов одновременно        |
| Применяется к   | Все эндпоинты, доступные API Key |

### 3.4 Сводная таблица лимитов

| Уровень                     | Идентификатор | Лимит           | Burst | Окно  |
| --------------------------- | ------------- | --------------- | ----- | ----- |
| Публичный (без авторизации) | IP            | 100 req/min     | 20    | 1 мин |
| Пользователь (JWT)          | user ID       | 600 req/min     | 100   | 1 мин |
| TMS интеграция (API Key)    | key ID        | 3000 req/min    | 500   | 1 мин |
| Platform Admin              | user ID       | Без ограничений | —     | —     |

## 4. Специальные лимиты по эндпоинтам

Некоторые эндпоинты имеют дополнительные ограничения поверх общих:

| Эндпоинт                                   | Доп. лимит                       | Причина                 |
| ------------------------------------------ | -------------------------------- | ----------------------- |
| `POST /api/v1/loads`                       | 30 создания / час на организацию | Предотвращение спама    |
| `POST /auth/login`                         | 10 попыток / 15 мин на IP        | Защита от брутфорса     |
| `POST /auth/refresh`                       | 60 / час на пользователя         | Защита от abuse         |
| `GET /api/v1/loads` (с параметрами поиска) | Входит в общий лимит             | —                       |
| `POST /api/v1/payments`                    | 20 / час на организацию          | Финансовая безопасность |

## 5. Заголовки ответа

К **каждому** ответу API добавляются заголовки состояния лимита:

```http
X-RateLimit-Limit: 600
X-RateLimit-Remaining: 543
X-RateLimit-Reset: 1710496860
X-RateLimit-Policy: authenticated;w=60
```

| Заголовок               | Тип     | Описание                                                |
| ----------------------- | ------- | ------------------------------------------------------- |
| `X-RateLimit-Limit`     | integer | Максимальное количество запросов в окне                 |
| `X-RateLimit-Remaining` | integer | Оставшееся количество запросов в текущем окне           |
| `X-RateLimit-Reset`     | integer | Unix timestamp сброса счётчика (начало следующего окна) |
| `X-RateLimit-Policy`    | string  | Описание применённой политики (tier;w=window_seconds)   |

## 6. Ответ при превышении лимита (429)

```http
HTTP/1.1 429 Too Many Requests
Content-Type: application/problem+json; charset=utf-8
X-RateLimit-Limit: 600
X-RateLimit-Remaining: 0
X-RateLimit-Reset: 1710496860
Retry-After: 23

{
  "type": "https://api.cargo.platform/errors/rate-limit-exceeded",
  "title": "Превышен лимит запросов",
  "status": 429,
  "detail": "Вы превысили лимит 600 запросов в минуту. Повторите запрос через 23 секунды.",
  "instance": "/api/v1/loads",
  "error_code": "RATE_LIMIT_EXCEEDED",
  "trace_id": "c3d4e5f6-a7b8-9012",
  "invalid_params": [],
  "retry_after_seconds": 23
}
```

**Заголовок `Retry-After`:**

- Значение в секундах до момента, когда запрос можно повторить.
- Обязателен при ответе `429`.
- Клиент **обязан** уважать этот заголовок и не отправлять запросы раньше указанного времени.

## 7. Стратегия для клиентов

### 7.1 Экспоненциальный backoff

```javascript
async function apiCallWithRetry(url, options, maxRetries = 3) {
  for (let attempt = 0; attempt < maxRetries; attempt++) {
    const response = await fetch(url, options);

    if (response.status !== 429) {
      return response;
    }

    const retryAfter = parseInt(response.headers.get("Retry-After") || "60");
    const jitter = Math.random() * 1000; // ±1 секунда случайного джиттера
    const waitMs = retryAfter * 1000 + jitter;

    console.log(
      `Rate limited. Waiting ${waitMs}ms before retry ${attempt + 1}`,
    );
    await sleep(waitMs);
  }
  throw new Error("Max retries exceeded");
}
```

### 7.2 Превентивный мониторинг

Клиенты должны отслеживать заголовок `X-RateLimit-Remaining` и снижать интенсивность запросов при приближении к лимиту (например, при `remaining < 10% от limit`).

### 7.3 Рекомендации для TMS-интеграций

- Использовать очереди запросов с контролем частоты на стороне клиента.
- Распределять запросы равномерно по минуте (не отправлять 3000 запросов мгновенно в начале окна).
- Кэшировать результаты справочников (города, типы грузов) локально на срок до 1 часа.

---

## 8. Исключения и белые списки

- Внутренние микросервисы платформы (machine-to-machine) не подпадают под Rate Limiting.
- Запросы Health Check эндпоинтов (`/health`, `/readiness`) не учитываются в лимитах.
- По запросу организации возможно предоставление индивидуальных лимитов (Enterprise SLA).
