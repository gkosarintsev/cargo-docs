# Миграции схем БД и Решение конкурентных коллизий

## Принципы Zero-downtime Database Migrations
1. **Паттерн Expand / Contract**:
   - Фаза 1: Добавление нового столбца.
   - Фаза 2: Двойная запись кодом приложения.
   - Фаза 3: Миграция старых данных.
   - Фаза 4: Чтение из нового столбца.
   - Фаза 5: Удаление старого столбца.
2. **Запрет тяжелых блокировок таблиц**:
   - `ADD COLUMN ... DEFAULT` без блокировки (Postgres 11+).
   - Создание индексов строго через `CREATE INDEX CONCURRENTLY`.
3. **Инструменты**:
   - Flyway / Liquibase / Goose с обязательной pre-deployment проверкой миграций в CI/CD (например, Squawk или pg-schema-diff).

## Защита от конкурентных конфликтов

### Сценарий 1: Два перевозчика одновременно принимают один груз
**Решение:** Optimistic Lock.
```sql
UPDATE loads SET status = 'BOOKED', version = version + 1 
WHERE id = ? AND version = ?;
```
Проигравший (получивший 0 обновленных строк) получает от API ошибку `409 Conflict`.

### Сценарий 2: Диспетчер в UI и внешняя TMS через API одновременно меняют заказ
**Решение:** Использование заголовка `If-Match: "<ETag_Version>"` в API. При несовпадении переданной версии с версией в базе данных возвращается ошибка `412 Precondition Failed`.

### Сценарий 3: Один водитель / машина назначены на два пересекающихся рейса
**Решение:** Транзакционная проверка в модуле Fleet Context с блокировкой календаря доступности:
```sql
SELECT * FROM driver_assignments 
WHERE driver_id = ? AND tsrange(start_time, end_time) && tsrange(?, ?) 
FOR UPDATE;
```
При пересечении бросается исключение.

### Сценарий 4: Пользователь повторно нажал кнопку отправки из-за таймаута
**Решение:** Использование заголовка `Idempotency-Key` (UUIDv4) в запросе. Сервер сохраняет ключи в Redis/PostgreSQL на 24 часа. При повторном запросе возвращается закэшированный ответ.

### Сценарий 5: Вебхук доставлен внешнему клиенту дважды
**Решение:** Уникальный `event_id` в теле вебхука. Клиент реализует паттерн Idempotent Receiver.

### Сценарий 6: Пакеты GPS пришли с нарушением порядка доставки
**Решение:** Обновление последней известной точки (`Current Position`) в Redis выполняется только если метка времени нового пакета больше текущей.
```lua
if packet.device_timestamp > redis.current_timestamp then
  redis.set(...)
end
```
