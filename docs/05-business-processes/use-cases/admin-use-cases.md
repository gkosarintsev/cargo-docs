# Use Cases: Администратор / Модератор платформы (Admin)

Этот документ описывает основные пользовательские сценарии для роли **Администратор** (Admin) платформы.

---

### UC-ADM-01: Верификация юридического лица (проверка выписки ЕГРЮЛ, налоговой отчетности, бенефициаров, судебных исков)

- **Основной актор**: Admin (Security Officer / Moderator)
- **Второстепенные акторы**: External KYC/KYB API (например, Контур.Фокус, Spark)
- **Цель (Goal in Context)**: Допустить к работе на платформе только надежные и законные компании.
- **Предусловия (Preconditions)**: Новая компания зарегистрировалась и загрузила уставные документы.
- **Триггер (Trigger)**: Появление новой заявки на верификацию в очереди (Onboarding Queue).
- **Основной успешный сценарий (Main Success Scenario - Happy Path)**:
  1. Актор открывает профиль компании, переданной на модерацию.
  2. Система автоматически подтягивает данные из внешних реестров (KYB API) по ИНН (статус юр. лица, наличие судов, долги по налогам).
  3. Актор сравнивает загруженные сканы документов с данными реестра.
  4. Риски не выявлены. Актор нажимает "Одобрить" (Approve).
  5. Профиль компании переводится в статус "Verified", открывается доступ к функциям платформы.
- **Альтернативные сценарии и исключения (Extensions / Alternative Flows)**:
  - 3a. Выявлены подозрительные факторы (например, компания в стадии банкротства) → Актор отклоняет заявку (Reject) с указанием причины (бан).
  - 3b. Не хватает документов → Актор возвращает заявку на доработку (Request Revisions), компания получает уведомление.
- **Постусловия (Postconditions)**:
  - _При успехе_: Компания верифицирована.
  - _При неудаче_: Доступ заблокирован или приостановлен.
- **Бизнес-правила и ограничения**: Неверифицированные пользователи имеют статус Read-only.

### UC-ADM-02: Модерация подозрительных грузов (Fraud Detection, проверка на дубликаты и скрапинг)

- **Основной актор**: Admin
- **Второстепенные акторы**: Anti-Fraud Engine
- **Цель (Goal in Context)**: Предотвратить мошенничество, дублирование грузов и "кражу" заявок.
- **Предусловия (Preconditions)**: Система анализирует публикуемые грузы.
- **Триггер (Trigger)**: Anti-Fraud Engine помечает груз флагом "Подозрительный" (Suspicious).
- **Основной успешный сценарий (Main Success Scenario - Happy Path)**:
  1. Актор получает алерт о публикации подозрительного груза (например, ставка сильно выше рынка или 100% совпадение маршрута и веса с чужим грузом - возможный диспетчер-перекуп).
  2. Актор изучает данные груза и профиль автора.
  3. Актор связывается с автором для уточнения (опционально).
  4. Актор признает груз фейковым и нажимает "Удалить/Заблокировать груз".
  5. Система скрывает груз из выдачи и снижает траст-скор аккаунта создателя.
- **Альтернативные сценарии и исключения (Extensions / Alternative Flows)**:
  - 2a. Актор определяет, что тревога ложная (False Positive) → Снимает флаг, груз продолжает публиковаться без ограничений.
- **Постусловия (Postconditions)**:
  - _При успехе_: Платформа очищена от фрода.
- **Бизнес-правила и ограничения**: Администратор может блокировать любой контент, нарушающий правила платформы.

### UC-ADM-03: Разбор диспутов и арбитраж претензий между грузовладельцем и перевозчиком

- **Основной актор**: Admin (Arbitrator)
- **Второстепенные акторы**: Shipper, Carrier
- **Цель (Goal in Context)**: Разрешить конфликтную ситуацию (порча груза, срыв погрузки, неоплата).
- **Предусловия (Preconditions)**: Одна из сторон открыла Dispute (претензию) по рейсу.
- **Триггер (Trigger)**: В дашборде арбитража появляется новый тикет.
- **Основной успешный сценарий (Main Success Scenario - Happy Path)**:
  1. Актор открывает тикет диспута и изучает претензию (например, перевозчик требует оплату за простой).
  2. Актор изучает логи GPS, историю чатов, подписанный договор и приложенные документы (акт о простое).
  3. Актор запрашивает дополнительные комментарии у второй стороны (грузовладельца) через систему тикетов.
  4. Актор выносит решение (например, удовлетворить требование перевозчика частично).
  5. Система фиксирует решение арбитража и инициирует взаиморасчеты/штрафы в биллинге.
  6. Диспут закрывается (Resolved).
- **Альтернативные сценарии и исключения (Extensions / Alternative Flows)**:
  - 3a. Стороны приходят к мировому соглашению до решения администратора → Сторона-инициатор закрывает диспут самостоятельно.
- **Постусловия (Postconditions)**:
  - _При успехе_: Конфликт разрешен, штрафы/компенсации распределены.
- **Бизнес-правила и ограничения**: Решение арбитража на платформе обязательно для исполнения, в противном случае следует блокировка аккаунта.

### UC-ADM-04: Блокировка аккаунта недобросовестной компании (Blacklisting) и аудит действий

- **Основной актор**: Admin
- **Второстепенные акторы**: Audit Log Service
- **Цель (Goal in Context)**: Изолировать нарушителей и изучить историю их действий.
- **Предусловия (Preconditions)**: Компания систематически нарушает правила (много проигранных диспутов, срывы).
- **Триггер (Trigger)**: Рейтинг компании падает ниже критической отметки или поступает жалоба о серьезном нарушении (мошенничество).
- **Основной успешный сценарий (Main Success Scenario - Happy Path)**:
  1. Актор открывает Audit Log для компании и анализирует историю действий.
  2. Актор подтверждает факт злостных нарушений.
  3. Актор нажимает "Заблокировать аккаунт" (Suspend/Ban) и указывает причину для внутренних логов.
  4. Система немедленно отменяет все активные публикации грузов/транспорта этой компании.
  5. Пользователи компании разлогиниваются, при попытке входа видят сообщение о блокировке.
- **Альтернативные сценарии и исключения (Extensions / Alternative Flows)**:
  - 3a. Временная блокировка → Актор задает срок блокировки (например, 7 дней). По истечении срока аккаунт автоматически размораживается.
- **Постусловия (Postconditions)**:
  - _При успехе_: Нарушитель изолирован от платформы.
- **Бизнес-правила и ограничения**: Блокировка компании не отменяет ее обязательств по уже выполняющимся (In Transit) рейсам и выставленным счетам.
