## Контекст

Завершающий раздел технической документации — **21-testing** (Этап 13).
Проектируем комплексную пирамиду тестирования для высоконадежной логистической платформы.
Особый упор делается на контрактное тестирование распределенных интеграций (Pact / AsyncAPI schemas), нагрузочное тестирование телематического контура и сценарии Chaos Engineering (из §32 master-prompt).

## Задание 1: создай `docs/21-testing/test-strategy.md`

### Содержимое документа (Сводная стратегия тестирования)

1. **Пирамида тестирования платформы (Testing Pyramid)**:
   - **Unit Tests (70%)**: Доменная логика, инварианты сущностей, калькуляторы тарифов, парсеры протоколов GPS. Быстрый прогон (< 30 сек).
   - **Integration / Component Tests (20%)**: Тестирование репозиториев с реальной БД (Testcontainers PostgreSQL), поиск в OpenSearch, продюсеры/консьюмеры Kafka.
   - **Contract Tests (5%)**: Проверка совместимости REST API и событий Kafka (Pact / Schema Registry).
   - **E2E / Scenario Tests (5%)**: Сквозные бизнес-цепочки через Playwright (Web) и Appium (Driver Mobile App).
2. **Quality Gates в CI/CD пайплайне**:
   - Покрытие кода тестами (Code Coverage) >= 80% для доменного слоя.
   - Отсутствие критических уязвимостей (SonarQube, Trivy).
   - 100% успешное прохождение контрактных тестов до деплоя.
3. **Матрица тестирования окружений**: Dev → CI → Staging (E2E & Load) → Production (Canary & Synthetic Monitoring).

## Задание 2: создай `docs/21-testing/contract-tests.md`

### Содержимое документа (Контрактное тестирование — КРИТИЧЕСКИЙ ДОКУМЕНТ)

1. **Consumer-Driven Contract Testing для REST API (Pact)**:
   - Как клиент (Web SPA / Mobile / Внешняя TMS) описывает контракт ожиданий.
   - Автоматическая верификация провайдером API (Бэкенд) на этапе CI. Предотвращение поломки мобильных приложений старых версий у водителей на линии.
2. **Контракты асинхронных сообщений Kafka (Schema Registry & Protobuf/JSON Schema)**:
   - Политика эволюции схем: `BACKWARD_TRANSITIVE` (новые консьюмеры всегда могут читать старые события; старые консьюмеры не падают при добавлении новых полей).
   - Проверка контрактов перед коммитом в репозиторий.
3. **Тестирование исходящих вебхуков**:
   - Mock-сервер для эмуляции клиентских TMS с задержками и сбоями для проверки логики ретраев и DLQ.

## Задание 3: создай `docs/21-testing/unit-tests.md`, `integration-tests.md` и `e2e-tests.md`

1. **`unit-tests.md`**:
   - Изоляция доменной модели от баз данных и фреймворков.
   - Паттерны: AAA (Arrange-Act-Assert), Property-Based Testing для проверки инвариантов сумм и габаритов.
2. **`integration-tests.md`**:
   - Использование `Testcontainers` (PostgreSQL, Kafka, Redis, OpenSearch, MinIO/LocalStack).
   - Тестирование Transactional Outbox: проверка записи в БД и корректной вычитки воркером.
   - Тестирование конкурентных блокировок (эмуляция 10 одновременных потоков на один груз).
3. **`e2e-tests.md`**:
   - Ключевые E2E сценарии:
     - Публикация груза Грузовладельцем → Поиск Перевозчиком → Подача и акцепт оффера → Заключение договора → Отметка водителем погрузки с фото → Трекинг → Отметка выгрузки с фото PoD → Выставление счета.

## Задание 4: создай `docs/21-testing/load-tests.md`, `chaos-tests.md` и `test-data.md`

1. **`load-tests.md` (Нагрузочное тестирование / k6, Locust, Gatling)**:
   - Сценарии нагрузки:
     - _Stress Test поисковой подсистемы_: 1 500 RPS гео-запросов к OpenSearch.
     - _High-Throughput GPS Ingestion_: 50 000 пакетов телеметрии/сек в Ingestion Gateway.
     - _Peak Day Marketplace_: одновременная публикация и торг 10 000 пользователей.
   - Критерии успешности (Pass/Fail criteria по latency p99 и error rate < 0.01%).

2. **`chaos-tests.md` (Тестирование хаосом / Chaos Engineering / Chaos Mesh)**:
   - Сценарии инъекции сбоев:
     - Убийство Primary ноды PostgreSQL под нагрузкой → проверка авто-failover Patroni без потери транзакций.
     - Искусственная задержка сети (Network Latency 2000ms) к Kafka → проверка буферизации в Outbox.
     - Отключение внешнего сервиса геокодинга → проверка Fallback кэша.
     - Сбой половины нод OpenSearch → проверка доступности чтения.

3. **`test-data.md` (Стратегия управления тестовыми данными)**:
   - Синтетические генераторы тестовых данных (Fake Logistics Data Generator: правдоподобные компании, ИНН, маршруты по реальной дорожной сети, GPS-треки).
   - Обезличивание (Sanitization / Anonymization) боевых данных для Staging окружения.
   - Изоляция тестовых данных (Test Tenancy) и автоматическая очистка после прогона тестов.
