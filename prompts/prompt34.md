## Задание 1: создай `docs/15-data/replication.md`

### Содержимое документа (Репликация и масштабирование БД)

1. **Топология репликации PostgreSQL**:
   - Primary Node (Read-Write) + 2 Синхронные/Полусинхронные реплики (High Availability с Patroni/etcd) + 2 Асинхронные Read-Replicas для тяжелых отчетов и чтения списков.
2. **Маршрутизация запросов (Read/Write Splitting)**:
   - Использование пулеров соединений (PgBouncer / Odyssey).
   - Принцип маршрутизации: мутирующие запросы и критическое чтение (Read-Your-Writes) идут строго на Primary; фильтрация каталогов и пагинация — на Read Replicas с контролем задержки репликации (Replication Lag < 100ms).

## Задание 2: создай `docs/15-data/search-index.md`

### Содержимое документа (Архитектура поискового индекса OpenSearch)

1. **Пайплайн индексации и синхронизации**:
   - `PostgreSQL (Transactional Outbox) → Kafka topic: marketplace.loads.v1 → OpenSearch Ingestion Worker (Batch Bulk Indexing) → OpenSearch Cluster`.
2. **Топология кластера OpenSearch**:
   - 3 Master-eligible nodes, 3 Data nodes, 2 Ingest/Coordinating nodes.
   - Конфигурация индексов: 5 Primary Shards + 1 Replica Shard.
3. **Обработка частичных обновлений и удалений**:
   - Partial Updates (обновление только цены или количества офферов без полной перезаписи документа).
   - Мягкое удаление (маркировка `is_active: false`) и периодический `delete_by_query`.
4. **Стратегия переиндексации без простоя (Zero-downtime Reindexing)**:
   - Использование индексов-алиасов (`loads_current` → `loads_v1`).
   - Пайплайн миграции: Создание `loads_v2` с новым маппингом → Reindex API → Прогрев → Атомарный переброс алиаса `loads_current` на `loads_v2` → Удаление `loads_v1`.

## Задание 3: создай `docs/15-data/retention.md` и `archival.md`

1. **`retention.md` (Политики хранения и очистки данных)**:
   - Таблица сроков хранения по типам данных:
     - Активные грузы/офферы: 30 дней после закрытия в горячей БД, затем выгрузка в архив.
     - GPS-точки высокой частоты (10 сек): 30 дней в горячем TimescaleDB, 1 год в агрегированном виде (1 мин), свыше 1 года — выгрузка в Parquet/S3.
     - Финансовые проводки, счета, eCMR: 5 лет в PostgreSQL (требование законодательства).
     - Логи аудита безопасности: 3 года.
2. **`archival.md` (Процесс архивации данных / Cold Storage)**:
   - Ежемесячные cron-джобы архивации старых завершенных заказов и телеметрии в формат Apache Parquet на S3.
   - Возможность холодного поиска по архиву через Presto / Trino / ClickHouse без раздувания оперативной БД.

## Задание 4: создай `docs/15-data/migrations.md`

### Содержимое документа (Миграции схем БД и Решение конкурентных коллизий)

1. **Принципы Zero-downtime Database Migrations**:
   - Паттерн Expand / Contract (Фаза 1: Добавление нового столбца → Фаза 2: Двойная запись кодом приложения → Фаза 3: Миграция старых данных → Фаза 4: Чтение из нового столбца → Фаза 5: Удаление старого столбца).
   - Запрет тяжелых блокировок таблиц: `ADD COLUMN ... DEFAULT` без блокировки (Postgres 11+), создание индексов строго `CREATE INDEX CONCURRENTLY`.
   - Инструменты: Flyway / Liquibase / Goose с обязательным pre-deployment проверкой в CI/CD.

2. **Защита от конкурентных конфликтов (из §21 master-prompt)**:
   Подробно специфицируй решения для каждого сценария:
   - **Сценарий 1: Два перевозчика одновременно принимают один груз**
     - _Решение_: `SELECT status, version FROM loads WHERE id = ? FOR UPDATE;` или Optimistic Lock `UPDATE loads SET status = 'BOOKED', version = version + 1 WHERE id = ? AND version = ?`. Проигравший получает `409 Conflict`.
   - **Сценарий 2: Диспетчер в UI и внешняя TMS через API одновременно меняют заказ**
     - _Решение_: Заголовок `If-Match: "<ETag_Version>"` в API. При несовпадении версии возвращается ошибка `412 Precondition Failed`.
   - **Сценарий 3: Один водитель / машина назначены на два пересекающихся рейса**
     - _Решение_: Транзакционная проверка в модуле `Fleet Context` с блокировкой календаря доступности (`SELECT ... FOR UPDATE` по строке водителя).
   - **Сценарий 4: Пользователь повторно нажал кнопку отправки из-за таймаута**
     - _Решение_: Ключ `Idempotency-Key` в заголовке запроса.
   - **Сценарий 5: Вебхук доставлен внешнему клиенту дважды**
     - _Решение_: Уникальный `event_id` в теле вебхука. Клиент сохраняет обработанные ID (Idempotent Receiver).
   - **Сценарий 6: Пакеты GPS пришли с нарушением порядка доставки**
     - _Решение_: Обновление последней точки ТС (`Current Position`) выполняется только если `packet.device_timestamp > redis.current_timestamp`.
