## Контекст

Продолжаем наполнение каталога Architecture Decision Records (ADR). На этом шаге рассматриваются ключевые инженерные решения для высоконагруженных и критических подсистем: телематики, матчинга, распределенной консистентности, идемпотентности и наблюдаемости.

Язык — **русский**. Формат — эталонный шаблон ADR.

---

## Задание: создай ADR с 0009 по 0015

### 1. `ADR-0009: Архитектура высоконагруженного контура приема GPS-телеметрии`

- **Проблема**: Необходимость стабильного приема и обработки десятков тысяч точек в секунду от трекеров и водительских смартфонов с нестабильной связью без деградации основной БД.
- **Альтернативы**: Direct Write в PostgreSQL с PostGIS; Direct Write в TimescaleDB через REST API; Выделенный Stateless Ingestion Gateway (Go/Rust) → Apache Kafka → Stream Processor → Redis (Current State) + TimescaleDB (Historical Track).
- **Решение**: Выделенный Ingestion Gateway со стримингом через Kafka. Обоснование: изоляция spike-нагрузок, буферизация при сбоях БД, сверхбыстрый ответ клиенту (202 Accepted).

### 2. `ADR-0010: Алгоритм и архитектура Matching Engine маркетплейса`

- **Проблема**: Автоматический подбор и ранжирование релевантных перевозчиков и машин под новые грузы.
- **Альтернативы**: Дорогостоящий Black-box ML/AI матчинг с первого дня; Простой SQL-поиск по фильтрам; Двухэтапный гибридный пайплайн: Hard Constraints Filtering (гео-радиус, тип кузова, грузоподъемность) → Deterministic Rule-based Scoring (рейтинг, пустой пробег, история надежности, ставка) с подготовкой данных для последующего ML-ранжирования.
- **Решение**: Двухэтапный детерминированный пайплайн с плавной эволюцией в ML.

### 3. `ADR-0011: Паттерн обеспечения надежной публикации событий (Transactional Outbox)`

- **Проблема**: Проблема двойной записи (Dual-write problem): как гарантировать, что транзакция в БД закоммичена И событие отправлено в Kafka без распределенных 2PC-транзакций.
- **Альтернативы**: Two-Phase Commit (XA/2PC); Публикация в брокер после коммита БД (риск потери события при падении сервиса); Паттерн Transactional Outbox с CDC (Debezium) или polling publisher.
- **Решение**: Transactional Outbox в единой транзакции с бизнес-данными + надежный Outbox Relay (Debezium / Tailer Worker) с семантикой At-Least-Once delivery.

### 4. `ADR-0012: Стратегия сквозной распределенной идемпотентности (Distributed Idempotency)`

- **Проблема**: Предотвращение повторного списания денег, дублирования заказов и повторного закрытия торгов при сетевых ретраях клиентов и повторной доставке сообщений из очередей.
- **Альтернативы**: Обработка «на удачу» без гарантий; Блокировка на уровне таблиц БД; Использование заголовка `Idempotency-Key` + распределенное хранение состояния запросов в Redis с блокировками (SETNX/Redlock) и проверкой уникальности в БД.
- **Решение**: Комплексная модель идемпотентности для API (Idempotency-Key + Redis TTL + Postgres unique constraint) и для Consumer событий (Idempotent Consumer pattern с дедупликацией по Event ID).

### 5. `ADR-0013: Стратегия многоуровневого кэширования (Multi-tier Caching)`

- **Проблема**: Снижение нагрузки на базу данных при чтении справочников, профилей и сессий при обеспечении приемлемой свежести данных.
- **Альтернативы**: Отсутствие кэширования; Только локальный in-memory кэш приложения; Распределенный Redis-кэш со стратегией Cache-Aside + инвалидация по событиям (Event-Driven Cache Eviction).
- **Решение**: Распределенный Redis кэш со стратегией Cache-Aside и подпиской на Domain Events для точечной инвалидации.

### 6. `ADR-0014: Стек сбора телеметрии и наблюдаемости (Observability: OpenTelemetry, Prometheus, Loki/ClickHouse, Tempo)`

- **Проблема**: Выбор единого стандарта и инструментов для метрик, логов и трассировок в распределенной системе.
- **Альтернативы**: Разрозненные проприетарные агенты (Datadog/NewRelic); Vendor-agnostic стандарт OpenTelemetry (OTel) + Prometheus / Grafana / Loki / Tempo.
- **Решение**: OpenTelemetry Instrumentation + Prometheus (метрики) + Loki (логи) + Tempo (трейсы) + Grafana.

### 7. `ADR-0015: Топология инфраструктуры и стратегия высокой доступности (HA Deployment Topology)`

- **Проблема**: Обеспечение непрерывности бизнеса при отказе целого дата-центра или зоны доступности облачного провайдера.
- **Альтернативы**: Single-AZ развертывание; Multi-AZ Active-Passive; Multi-AZ Active-Active для stateless компонентов + Multi-AZ Synchronous/Semi-synchronous репликация для БД и Kafka с автоматическим кворумом.
- **Решение**: Multi-AZ развертывание (3 зоны доступности) с автоматическим failover через Patroni для PostgreSQL.
